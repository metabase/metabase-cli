# Changelog

Notable changes to `@metabase/client`.

## 0.1.7

- `ClientCredentials.credential` is a `TransportCredential`: a `Credential`, a `SessionCredential` or an `AnonymousCredential`. A `SessionCredential` sends its session id as `X-Metabase-Session` and is never refreshed, so a call made after the session expires fails with an `HttpError` of kind `auth`. An `AnonymousCredential` sends no auth header, which is enough for the health check, the public session properties, setup and login. A 401 names what the server refused: an invalid or expired session, or a request that carried no credential. `Credential`, what `refreshCredential` answers, is unchanged.
- `session.create` logs in with a username and password and answers the new session's id as a `Session`.
- `health.get` answers the server's `Health` (`GET /api/health`). A 503 carrying the `initializing` or app-database body is returned as the answer rather than thrown, and the call does not retry unless `retries` is set, so a caller polling a booting server reads each step.
- `session.settings` reads the session properties as `SessionSettings`, the settings a caller bringing up an instance reads: `has-user-setup`, `setup-token`, `mcp-enabled?` and `ai-features-enabled?`, and, where the caller can read them, `site-name` and `remote-sync-enabled`. The answer is parsed by the shape of the server that sends it: the two AI switches are `null` on a server without the `aiFeatureSwitches` feature, which holds from Metabase 60.
- `permission.groups` lists the permission groups as `PermissionGroup`.
- `user.list` lists the users as `User`, filtered by `status` (`UserListStatus`: `active`, `deactivated` or `all`), `query` and `group_id`. `user.create` creates a user from a `UserCreateInput`.
- `gitSync.updateSettings` configures the remote, the sync direction, the tracked branch, auto-import, `remote-sync-transforms` and the synced collections (`SyncSettingsUpdateParams`). Metabase 59 to 65 take `remote-sync-transforms`. Metabase 58 and the development line drop the key unread and answer as if it had never been sent, so there the call is refused before the request with a `CapabilityError` naming `remoteSyncTransformsSetting`, unless the caller skips such refusals (`onPreflightSkipped`).
- `task.runPages` walks the background-job runs as `TaskRun`, filtered by run type, entity, status and start time. It needs `taskRuns`, which holds from Metabase 59.
- `workspaceManager.list`, `workspaceManager.get`, `workspaceManager.create`, `workspaceManager.delete` and `workspaceManager.config` manage workspaces (`Workspace`, `WorkspaceDatabase`), and `workspaceInstance.current` answers the `WorkspaceInstance` loaded on the instance, or `null`. All of them need the `workspaces` feature, which the `workspaces` token grants.
- `Database` reads `features`, `settings` and `initial_sync_error`. A `settings` value of the wrong type, such as a string for `database-enable-actions`, fails the parse, as it already did for `DatabaseWithSettings`.
- `createClient` takes a `trustedServer`: a profile the caller probed itself and vouches for. The client takes it as its own probe's answer, so a gated parameter, a method refused before the request and an explained refusal all judge by it, and no call reads `/api/session/properties` to verify it. A `server` handed in is still a cache the client verifies before any verdict. The two are exclusive.
- `client.with({ userAgent, signal, guard, onError })` answers a client on the same transport: the same credential and its refresh, and the same server profile and probes, so it probes nothing its parent holds. Its `userAgent` replaces the parent's on every request it sends. Its `signal` ends its requests and waits as well as the parent's does, its `guard` runs after the parent's, and its `onError` runs before the parent's. A derived client can derive another. A probe of the server's profile is shared and runs as the client `createClient` made.
- `ClientOptions.guard` (`RequestGuard`) is shown each request before it is sent, as a `GuardedRequest` (`method`, and `path` without the query string), and may refuse it by throwing. What it throws reaches the caller as thrown, never as a `NetworkError`. A retry, or the resend after a credential refresh, is not shown again.
- `ClientOptions.onError` (`ErrorObserver`) is shown every error a call on the client raises before the caller sees it: a throw, a rejection, or a failure while walking a list. It is not awaited, and one that throws fails the call with its own error.
- Every wait a call runs (`transform.run`, `database.syncSchema` and the git-sync calls given `wait`, and `gitSync.waitForTask`) ends when the client's signal, the call's `signal` or the wait's own `signal` aborts, whichever comes first, sleep included. Each read in the wait carries the call's options. `Transport.signal` is the client's own signal.
- `PollOptions.timeoutMs` takes `null` for a wait with no deadline, which ends only when its condition holds or a signal aborts. A timeout, interval or maximum interval above `MAX_TIMER_MS` (2,147,483,647 ms, the longest a timer keeps) is refused with a `ConfigError` before the wait starts, where Node would have fired it after 1 ms. `startDeadline` and `pollWithin` on `@metabase/client/poll` run several waits under one `Deadline`.
- `transform.run` with `syncTarget` waits for the run and then for the output table under the one deadline `wait.timeoutMs` sets, or under none when it is `null`. The deadline starts before the run does, so a timeout no timer can keep is refused before anything runs.
- `collection.summaries` lists the collections the caller can read, the Library among them, as `CollectionSummary` (`id`, `name`, `location`, `personal_owner_id`, `archived`, `is_remote_synced`, `entity_id`). It reads no enum, so a collection whose `type`, `namespace` or `authority_level` this client does not know fails nothing. `archived: true` lists the archived collections instead (`CollectionSummaryParams`).
- `gitSync.hasRemoteChanges` reads a server that keeps no cache of the comparison, such as the development line, which sends no `cached`: its answer reads `cached: false`, since it reads the remote on every call. `SyncRemoteChanges.branch_missing` is present, and true, when the tracked branch is gone from the remote. `force-refresh` still re-reads the remote on a server with `remoteSyncChangesCache` (59 to 65), and one without it drops the key. `syncRemoteChangesSchema` is the reader.
- `SyncTask` reads `outcome`, `initiated_by_user` and `last_heartbeat_at`. `outcome` is a `SyncTaskOutcome`, a union on `kind`: `pulled` or `pushed` (each with `count` and `branch`), `merged` (`pulled`, `pushed`, `branch`), `pull-skipped`, `push-skipped`, `remote-changed` or `history-rewritten`. It is `null` while the task runs, after a failure, and on a server without `remoteSyncTaskOutcome` (63). `initiated_by_user` (`SyncTaskInitiator`: `id`, `first_name`, `last_name`, `email`) and `last_heartbeat_at` are `null` when there is none, and on a server without `remoteSyncTaskHeartbeat` (65). `syncTaskSchema` is the reader `gitSync.currentTask`, `gitSync.cancelTask` and every wait on a task use.
- `SyncDirtyItem` reads the development line's changed items, which name their collection in full. `collection` (`SyncItemCollection`: `id`, `name`, `type`, and `effective_ancestors` root-most first) is the item's collection, or a collection itself, and `model_id` is the model an action belongs to. On a server with `remoteSyncDirtyItemsByCollectionId` (58 to 65), which names the collection by id alone, both read `null`. `collection_id` holds the collection's id on every server. `syncDirtyItemSchema` is the reader.
- `gitSync.import`, `gitSync.export`, `gitSync.exportPreflight`, `gitSync.updateSettings` and `gitSync.setCollectionSynced` throw `SyncRefusedError` for a refusal the server marks as git-sync's own. It is the `HttpError` the server answered, with `refusal`, a `SyncRefusal` union on `kind`. `dirty` is an import refused on changes not yet pushed: a 400 with `conflicts`, and `dirty_objects` as `SyncDirtyItem`s, `null` on a server without `remoteSyncImportNamesDirtyObjects` (64), which names none. `unsynced-dependencies` is a settings update refused on content the synced collections use but which is not synced: the development line's 400 with `error-code` and `unsynced_dependencies` (`SyncUnsyncedDependency`). `branch-mismatch` is a call naming a branch other than the tracked one: the 409 with `branch_mismatch` and `current_branch`, from 63. A server that hides stack traces answers these with a bare message, which stays an `HttpError`, and so does 64's `error_code` form of the unsynced-dependencies refusal. `HttpError`'s constructor also takes an `HttpError`, so a subclass can take over an answer already read.
- `gitSync.createBranch` says that only Metabase 58 to 65 route `POST /create-branch`. The development line answers it with an `HttpError` of kind `route-missing`, and makes a branch only through `gitSync.stash`.
- `gitSync.testConnection` checks that the remote answers to the saved URL and token, or to those given (`SyncTestConnectionParams`), without saving them, and answers `SyncConnectionTested`. A remote the server cannot reach is its 400, with its reason. It needs `remoteSyncTestConnection`, which holds from Metabase 62 with the `remote_sync` token.

## 0.1.6

- A data app names its slug and its display name as its `data_app.yaml` does: `DataApp`, `DataAppSummary` and `DataAppCompact` read the slug from `slug` and the display name from `name`, which held the slug, and have no `display_name`.

## 0.1.5

- `session.properties()` returns the server's session properties (`GET /api/session/properties`): the settings the caller may read, including the server's version and the premium features its license grants. It always sends the request, never answering from a profile the client holds. The client treats the answer as it treats its own probe of the server: the answer becomes the profile `client.server()` and `client.verifiedServer()` return, and is passed to `onServerProbed`.

## 0.1.4

- A data app changes in Metabase only through a repository import, so `dataApp.create`, `dataApp.replaceBundle`, `dataApp.typedSchema` and `dataApp.remove` are gone, with `DataAppCreateInput`. `dataApp.update` takes only `enabled` (`DataAppUpdateInput`).
- `dataApp.list` takes no filter, and `DataAppListFilter` is gone.
- `dataApp.generateSchema`, `dataApp.generateQueries` and `dataApp.generateActions` return the files of an app's repository as `DataAppGeneratedFiles`: its `src/metabase.schema.ts`, and the YAML of the questions and implicit actions its `defineQuery` and `defineAction` exports define (`DataAppGenerateQueriesInput`, `DataAppGenerateActionsInput`, `DataAppQueryDefinition`, `DataAppActionDefinition`).

## 0.1.3

- `dataAction.create` creates an implicit action on a table as well as a query action. `DataActionCreateInput` is a union on `type`: a `"query"` body takes `dataset_query`, an `"implicit"` one takes `kind` (`ImplicitActionKind`, on the barrel) and `table_id`. Neither takes `database_id`, which the server derives from the query.
- `DataActionUpdateInput` patches a query action's `dataset_query` or an implicit action's `kind` and `table_id`, never both, and takes no `database_id`. `dataAction.update` refuses a `table_id` before the request on a server without `dataActionsWithoutModel`, which would drop it unread; `DATA_ACTION_TABLE_GATE` records the gate.
- `DataAction` and `DataActionCompact` read an implicit action's `kind` and `table_id`.
- `DataActionExecuteResult` reads an implicit action's `rows-updated`, `rows-deleted` or `created-row`, and `rows-affected` is optional.

## 0.1.2

- `oauthLogin` takes an optional `signal`. Aborting it, before or during the flow, rejects with the signal's reason when that is a `MetabaseError`, else with an `AbortError` carrying its message, frees the loopback callback port at once, and cancels discovery, client registration or the token exchange in flight. `tryDiscoverMetadata`, `discoverLoginMetadata`, `registerClient` and `exchangeCode` on `@metabase/client/http/oauth` take a signal too, and `@metabase/client/signal` exports `whenAborted`.

## 0.1.1

- `DashboardCreateInput` holds only the fields `POST /api/dashboard` reads, so a layout passed to `dashboard.create` fails to compile; send it as a `DashboardLayoutInput` through `dashboard.update`. At run time `dashboard.create` drops any other key before the request, as the server does, and refuses a blank `name`, as the server does.
- `DashboardLayoutInput` and `DatabaseUpdateInput` are on the barrel.
- `@metabase/client/json-pointer` exports `unescapeJsonPointerSegment`, the inverse of `escapeJsonPointerSegment`.
- `@metabase/client/version/input-gates` exports the input gates recorded on feature-gated body fields, with `gateTriggered` and `inputGatesOf`, and `featureAvailability` says which servers hold a feature.
- `dataAction.update` refuses a `collection_id` before the request on a server without `dataActionCollections`, which would drop it unread.
- `dashboard.get` and `dashboard.update` read a dashboard holding a text, heading or other dashcard bound to no card. The server answers a stub `card` such as `{ query_average_duration: null, download_perms: "none" }` for such a dashcard, which 0.1.0 refused; it reads as `null`, and `dashboardDetailSchema` on the dashboard subpath is the reader.
- A transform's Python `source-tables` entry reads without `database_id` or `schema`, as the server stores an entry whose table or database is gone. `TransformSourceTableEntry` is the stored entry, and `TransformSourceTableEntryInput`, on the barrel, is the entry the create, update and Python test-run bodies take, as strict as before.
- Every transform read on Metabase 59 accepts a Python transform, whose `source-tables` that server keys by alias. `transformRowSchema` and `transformDetailSchema` read it as the list later servers answer, taking each alias from its key; an entry naming its table by id alone reads `database_id`, `schema` and `table` as `null`, and one whose table that server could not find reads `table_id` as `null` too. `transformSourceTablesAsList` is the feature.
- The dependency readers accept the action nodes Metabase 65 adds: `DependencyType` and `DependencyUsageType` take `"action"`, and `DependencyEntityData.type` takes an action's `"implicit"` or `"query"`. `dependency.graph`, `dependency.dependents` and `dependency.broken` explain an older server's refusal of an action as the entity through `actionDependencyGraph`.
- `notification.get`, and the `update`, `archive` and `send` that read through it, refuse a dashboard subscription with the "not a question alert" `ConfigError` instead of a shape error on its payload. `AnyNotification` is the reader: a question alert in full, any other type read no further than `id` and `payload_type`. `CARD_PAYLOAD_TYPE` has the literal type `"notification/card"`.
- `CurrentUser.email` is any string, so `user.current` reads an account whose address Metabase accepts and a stricter email check refuses, such as one with `!` or `/` in the local part or a digit or one-letter top-level domain.
- `transform.create`, `transform.update` and `transformPython.testRun` send a Python source's tables keyed by alias to Metabase 58 and 59, which read no list: a transform entry as its reference less `alias`, which 59 reads and 58, taking only table ids, refuses, or as the bare table id when it names its table by id alone, and a test-run entry as its table id. `TransformSourceTableEntryInput` also takes that id-only entry, `{ alias, table_id }` with `database_id`, `schema` and `table` absent or `null`, so a transform read from 59 updates back unchanged. `pythonTestRun` holds from 58 on a server licensed for Python transforms.
- `SetupInput.user.email` is any string, so `setup.create` hands Metabase an address it accepts and a stricter email check refuses, and the server judges it.
- `collection.itemPages` walks the `trash` alias on every server. No Metabase routes `/api/collection/trash/items`, so the walk reads the trash collection's id from `GET /api/collection/trash` first and pages its items by that id.
- `search.query` and `collection.itemPages` explain an older server's 400 for a `models` value it does not take as the feature it lacks: `measure` in search through `measures`, `transform` through `transforms`, `exploration` through the new `explorations`, and among collection items `measure` through the new `collectionItemMeasures`.
- `collection.itemPages` applies `pinned_state` on Metabase 64 and later, which read it as `pinned-state` and drop the spelling 58 through 63 read.
- `TransformJobUpdateInput.active` records that it needs `transformJobActivation`; a server before 61 drops it unread and still answers the job as active.
- `LibraryPublishTablesInput.collection_id` records that only a server with `tablePublishTargetCollection` (62+) reads it; an older one publishes into its one Library data collection. It is sent on every server.
