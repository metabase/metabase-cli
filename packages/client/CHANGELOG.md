# Changelog

Notable changes to `@metabase/client`.

## 0.1.10

- `HttpError.specificFieldErrors` reads Metabase's `specific-errors` for a query: Malli's explanation, which mirrors the value it explains and holds `null` where a list item fits. Each refused part is keyed by its path, map keys dot-joined and list items by index (`stages[0].aggregation[1][2]`), and a sentence Metabase repeats for one part is kept once. A field the server rejects as a whole is keyed as before (`name`, `prefs.site_locale`).
- An error Malli files against a map as a whole, under its `malli/error` key, is keyed by the map's own path (`stages[0]`, not `stages[0].malli/error`), its sentences joined with any others at that path, in `specificFieldErrors`, `fieldErrors` and the message alike.
- When every sentence about one part quotes the same value, the field message says it once, at the end (`should be a string; should be a positive int, received: 0`), in `specificFieldErrors`, `fieldErrors` and the message alike.
- `HttpError.fieldErrors` reads `errors` with the same shape, `null` items and nested lists included, keyed the same way: a row-editing validation answering `{"12": [null, {"created_at": "…"}]}` gives `12[1].created_at` rather than `fieldErrors: null`. For a query, `errors` describes the schema each part had to fit and names map keys alone (`stages.aggregation`).
- Each message in `fieldErrors` and `specificFieldErrors` is at most 4,096 characters, cut with `…`, so the schema description past 1 MB that `errors` carries for a bad field ref reaches `developerDetail` as 4 KB.
- The message of a 400 refusing a query names each refused part and what Metabase said arrived there (`stages[0].aggregation[1][2][2]: should be a string; should be a positive int, received: 0`) rather than the schema the part had to fit (`stages.aggregation: function`). Each part is condensed on its own, a `received:` value past 60 characters cut with `…`, and whole parts are listed while they fit in 500 characters, the rest counted (`; and 3 more`), so one long value never crowds out the parts after it; only a first part longer than that on its own is cut.
- An `HttpError` reads its message and `serverMessage` from the whole error body, like every other view. A 400 whose body runs past 64 KB, such as the 1 MB answer to a query with a bad field ref, gives the server's reason rather than `Metabase returned 400.`, and a 500 whose stack trace runs past 64 KB gives its `message`, cut to 500 characters, rather than `Metabase returned 500.`; `serverMessage` is that reason rather than `null`. A consumer matching either status default to recognise such a body matches the server's reason instead. `developerDetail.body` is still the first 64 KB.
- A consumer matching `specificFieldErrors` keys, or `fieldErrors` keys, against request fields reads the field a key starts at up to its first `.` or `[`; `topLevelField` on `@metabase/client/http/errors` answers it.

## 0.1.9

- `task.run` reads one background-job run with its tasks as `TaskRunWithTasks`: the `TaskRun` and its `tasks`, oldest first, each a `TaskHistory` (`id`, `task`, `db_id`, `started_at`, `ended_at`, `duration`, `status` and `task_details`). `status` is a `TaskHistoryStatus`: `started`, `success`, `failed` or `unknown`. `task_details` is the task's own record, `TaskHistoryDetails`, whose `message`, when the task failed, holds the first 250 characters of the exception's message, or null when the exception had none. It needs `taskRuns`, which holds from Metabase 59, and the monitoring application permission.
- `TaskRun` always carries `entity_name`, `task_count`, `success_count` and `failed_count`, from `task.runPages` and `task.run` alike: every server that lists runs sends them. `entity_name` is null when the entity no longer exists.

## 0.1.8

- `ClientCredentials.credential` is a `TransportCredential`: a `Credential`, a `SessionCredential` or an `AnonymousCredential`. A `SessionCredential` sends its session id as `X-Metabase-Session` and is never refreshed, so a call made after the session expires fails with an `HttpError` of kind `auth`. An `AnonymousCredential` sends no auth header, which is enough for the health check, the public session properties, setup and login. A 401 names what the server refused: an invalid or expired session, or a request that carried no credential. `Credential`, what `refreshCredential` answers, is unchanged.
- `session.create` logs in with a username and password and answers the new session's id as a `Session`.
- `health.get` answers the server's `Health` (`GET /api/health`). A 503 carrying the `initializing` or app-database body is returned as the answer rather than thrown, and the call does not retry unless `retries` is set, so a caller polling a booting server reads each step.
- `session.settings` reads the session properties as `SessionSettings`, the settings a caller bringing up an instance reads: `has-user-setup`, `setup-token`, `mcp-enabled?` and `ai-features-enabled?`, and, where the caller can read them, `site-name` and `remote-sync-enabled`. The answer is parsed by the shape of the server that sends it: the two AI switches are `null` on a server that does not report them, which is every server before Metabase 60.1.
- `permission.groups` lists the permission groups as `PermissionGroup`.
- `user.list` lists the users as `User`, filtered by `status` (`UserListStatus`: `active`, `deactivated` or `all`), `query` and `group_id`. `user.create` creates a user from a `UserCreateInput`.
- `gitSync.updateSettings` configures the remote, the sync direction, the tracked branch, auto-import, `remote-sync-transforms` and the synced collections (`SyncSettingsUpdateParams`). Metabase 59 to 65 take `remote-sync-transforms`. Metabase 58 and every server from 66 drop the key unread and answer as if it had never been sent, so there the call is refused before the request with a `CapabilityError` naming `remoteSyncTransformsSetting`, unless the caller skips such refusals (`onPreflightSkipped`).
- `task.runPages` walks the background-job runs as `TaskRun`, filtered by run type, entity, status and start time. It needs `taskRuns`, which holds from Metabase 59.
- `workspaceManager.list`, `workspaceManager.get`, `workspaceManager.create`, `workspaceManager.delete` and `workspaceManager.config` manage workspaces (`Workspace`, `WorkspaceDatabase`), and `workspaceInstance.current` answers the `WorkspaceInstance` loaded on the instance, or `null`. All of them need the `workspaces` feature, which holds from Metabase 66 with the `workspaces` token.
- `Database` reads `features`, `settings` and `initial_sync_error`. A `settings` value of the wrong type, such as a string for `database-enable-actions`, fails the parse, as it already did for `DatabaseWithSettings`.
- `createClient` takes a `trustedServer`: a profile the caller probed itself and vouches for. The client takes it as its own probe's answer, so a gated parameter, a method refused before the request and an explained refusal all judge by it, and no call reads `/api/session/properties` to verify it. A `server` handed in is still a cache the client verifies before any verdict. The two are exclusive.
- `client.with({ userAgent, signal, guard, onError })` answers a client on the same transport: the same credential and its refresh, and the same server profile and probes, so it probes nothing its parent holds. Its `userAgent` replaces the parent's on every request it sends. Its `signal` ends its requests and waits as well as the parent's does, its `guard` runs after the parent's, and its `onError` runs before the parent's. A derived client can derive another. A probe of the server's profile is shared and runs as the client `createClient` made.
- `ClientOptions.guard` (`RequestGuard`) is shown each request before it is sent, as a `GuardedRequest` (`method`, and the `path` the request goes to, with dot segments resolved and without the query string), and may refuse it by throwing. What it throws reaches the caller as thrown, never as a `NetworkError`. A retry, or the resend after a credential refresh, is not shown again. A guard that refuses the probe of `/api/session/properties` a check before the request needs fails the call with what it threw, even when the caller skips such checks (`onPreflightSkipped`), rather than letting the call go on unchecked. When the guard refuses the probe that explains an error the server already answered, the call fails with the server's answer, unexplained. A guard runs synchronously and answers `undefined`, so an async guard fails to compile, and a guard that answers a promise all the same refuses every request with a `ConfigError` before it is sent.
- `ClientOptions.onError` (`ErrorObserver`) is shown every error a call on the client raises before the caller sees it: a throw, a rejection, or a failure while walking a list. It is not awaited. Every observer sees the original error, a derived client's and then its parent's, even when one before it throws; the call then fails with the error the first observer to throw threw. It answers `undefined`, so an async observer fails to compile, and one that answers a promise all the same fails the call with a `ConfigError`.
- `createTransport` takes `TransportOptions`, `ClientOptions` without `onError`, and `Transport.with` takes `DerivedTransportOptions`, `DerivedClientOptions` without `onError`. A transport has no calls of its own to observe, so passing `onError` to either is a compile error rather than an observer never called. `createClient` and `client.with` take `onError` as before.
- `Transport.refusedByGuard` says whether an error is what a request guard threw, so a resource can tell the caller's own refusal from a server out of reach.
- Every wait a call runs (`transform.run`, `database.syncSchema` and the git-sync calls given `wait`, and `gitSync.waitForTask`) ends when the client's signal, the call's `signal` or the wait's own `signal` aborts, whichever comes first, sleep included. Each read in the wait carries the call's options. `Transport.signal` is the client's own signal.
- `PollOptions.timeoutMs` takes `null` for a wait with no deadline, which ends only when its condition holds or a signal aborts. A `timeoutMs`, `intervalMs` or `maxIntervalMs` that is not a finite, non-negative number, or is above `MAX_TIMER_MS` (2,147,483,647 ms, the longest a timer keeps, where Node would fire a longer one after 1 ms), is refused with a `ConfigError` naming the field. A call that starts work and then waits on it (`transform.run`, `database.syncSchema`, and `gitSync.import`, `gitSync.export` and `gitSync.stash` given `wait`) refuses it before its first request, so it starts nothing, and `pollUntil`, `pollWithin` and `gitSync.waitForTask` refuse it before the first poll. `checkSchedule` on `@metabase/client/poll` is that check. `startDeadline` and `pollWithin` there run several waits under one `Deadline`, and `startDeadline` checks the whole schedule it is handed before it starts the deadline.
- `transform.run` with `syncTarget` waits for the run and then for the output table under the one deadline `wait.timeoutMs` sets, or under none when it is `null`. The deadline starts before the run does, so a schedule no timer can keep is refused before anything runs.
- `collection.summaries` lists the collections the caller can read, the Library among them, as `CollectionSummary` (`id`, `name`, `location`, `personal_owner_id`, `archived`, `is_remote_synced`, `entity_id`). It reads no enum, so a collection whose `type`, `namespace` or `authority_level` this client does not know fails nothing. `archived: true` lists the archived collections instead (`CollectionSummaryParams`).
- `gitSync.hasRemoteChanges` reads a server that keeps no cache of the comparison, Metabase 66 and later, which sends no `cached`: its answer reads `cached: false`, since it reads the remote on every call. `SyncRemoteChanges.branch_missing` is present, and true, when the tracked branch is gone from the remote. `force-refresh` still re-reads the remote on a server with `remoteSyncChangesCache` (59 to 65), and one without it drops the key. `syncRemoteChangesSchema` is the reader.
- `SyncTask` reads `outcome`, `initiated_by_user` and `last_heartbeat_at`. `outcome` is a `SyncTaskOutcome`, a union on `kind`: `pulled` or `pushed` (each with `count` and `branch`), `merged` (`pulled`, `pushed`, `branch`), `pull-skipped`, `push-skipped`, `remote-changed` or `history-rewritten`. It is `null` while the task runs, after a failure, and on a server without `remoteSyncTaskOutcome` (63). `initiated_by_user` (`SyncTaskInitiator`: `id`, `first_name`, `last_name`, `email`) and `last_heartbeat_at` are `null` when there is none, and on a server without `remoteSyncTaskHeartbeat` (65). `syncTaskSchema` is the reader `gitSync.currentTask`, `gitSync.cancelTask` and every wait on a task use.
- `SyncDirtyItem` reads the changed items of a server from Metabase 66, which describe each item by its hydrated row (`data`): `collection` (`SyncItemCollection`: `id`, `name`, `type`, and `effective_ancestors` root-most first, the root collection left out) is read from where the item's model holds it, such as a segment's table, and is the item's collection, or a collection itself, `null` for an item in the root collection or one whose row is gone; `model_id` is the model an action belongs to. On a server with `remoteSyncDirtyItemsByCollectionId` (58 to 65), which names the collection by id alone, `collection` reads `null`; `model_id` is read from the `card_id` Metabase 65 sends for an action, and is `null` on 58 to 64, which do not say. `collection_id` holds the collection's id on every server. `syncDirtyItemSchema` is the reader.
- `gitSync.import`, `gitSync.export`, `gitSync.exportPreflight`, `gitSync.updateSettings` and `gitSync.setCollectionSynced` throw `SyncRefusedError` for a refusal the server marks as git-sync's own. It is the `HttpError` the server answered, with `refusal`, a `SyncRefusal` union on `kind`. `dirty` is an import refused on changes not yet pushed: an import's 400 with `conflicts`, and `dirty_objects` as `SyncDirtyItem`s, `null` on a server without `remoteSyncImportNamesDirtyObjects` (64), which names none. An export's 400 with `conflicts`, which Metabase 58 to 62 answer when the remote branch moved since the last sync, stays an `HttpError`. `unsynced-dependencies` is a settings update refused on content the synced collections use but which is not synced: the 400 with `error-code` and `unsynced_dependencies` (`SyncUnsyncedDependency`: `id`, `model`, `name`, `collection` and `used_by`, read from each item's hydrated row, with `name` `null` where the row names it nothing) that a server from Metabase 66 answers. `branch-mismatch` is a call naming a branch other than the tracked one: the 409 with `branch_mismatch` and `current_branch`, from 63. A server that hides stack traces answers these with a bare message, which stays an `HttpError`, and so does the `error_code` form of the unsynced-dependencies refusal that 64 and 65 answer. `HttpError`'s constructor also takes an `HttpError`, so a subclass can take over an answer already read.
- An `HttpError` reads its `fieldErrors`, `specificFieldErrors`, `errorCode`, `nonRemoteSyncedDependencies`, `remoteSyncedDependents`, `tables` and `kind` from the whole error body, and a `SyncRefusedError` its `refusal`, so a refusal naming hundreds of items under a stack trace is read in full. Its message and `serverMessage` are read from the first 64 KB alone, so a JSON body longer than that, such as the stack trace around a malformed query's schema dump, keeps the status's own message. `developerDetail.body` is the first 64 KB of the body, cut after known secrets are redacted and at a character boundary. An error body is read up to 8 MB and the rest of the response is dropped unread; a JSON body longer than that is an `HttpError` with the status's own message.
- `gitSync.createBranch` says that only Metabase 58 to 65 route `POST /create-branch`. A server from Metabase 66 answers it with an `HttpError` of kind `route-missing`, and makes a branch only through `gitSync.stash`.
- `gitSync.testConnection` checks that the remote answers to the saved URL and token, or to those given (`SyncTestConnectionParams`), without saving them, and answers `SyncConnectionTested`. A remote the server cannot reach is its 400, with its reason. It needs `remoteSyncTestConnection`, which holds from Metabase 62 with the `remote_sync` token.
- A server from Metabase 66, release or development build, is past the rules that end at 65: `remoteSyncChangesCache`, `remoteSyncDirtyItemsByCollectionId` and `remoteSyncTransformsSetting` hold on none of them. `workspaces` holds from 66.
- A `CapabilityError` for a feature whose rule ended before the server's major says so: its `RequirementFailure` has `reason` `"version-too-new"` (`RequirementReason`) and a `detail` that names the last major holding the feature and says the server is too new for it. `gitSync.updateSettings` with `remote-sync-transforms` on a server from Metabase 66 is refused this way. `featureGap` and `ruleGap` answer `{ kind: "ended", until }` (`EndedGap`) for such a server.

## 0.1.7

- `dataApp.create` creates an app with its resource collection and an empty bundle (`DataAppCreateInput`, which takes the slug as `slug`), `dataApp.updateBundle` replaces its bundle with the text of a built bundle, and `dataApp.delete` deletes it with its collection. `dataApp.getBundle` reads an app's bundle as the text of its built JavaScript. `DataAppUpdateInput` takes the app's name, description, version, bundle path and allowed hosts as well as `enabled`.
- `KNOWN_RANGE` reaches 65, so a newer server reads as 66. `dataApp.create`, `updateBundle` and `delete` need Metabase v66 (the `dataAppEditing` feature), and a refusal from an older server is explained as such. `dataApp.update` refuses a manifest field before the wire on an older server, which takes `enabled` alone (`DATA_APP_EDITING_GATE`).
- `DataAppSummary`, what a non-admin reads, carries the app's `id`, `enabled` and `outdated`, and `DataAppCompact` its `id`.

## 0.1.6

- A data app names its slug and its display name as its `data_app.yaml` does: `DataApp`, `DataAppSummary` and `DataAppCompact` read the slug from `slug` and the display name from `name`, which held the slug, and have no `display_name`.

## 0.1.5

- `session.properties()` returns the server's session properties (`GET /api/session/properties`): the settings the caller may read, including the server's version and the premium features its license grants. It always sends the request, never answering from a profile the client holds. The client treats the answer as it treats its own probe of the server: the answer becomes the profile `client.server()` and `client.verifiedServer()` return, and is passed to `onServerProbed`.

## 0.1.4

- A data app changes in Metabase only through a repository import, so `dataApp.create`, `dataApp.replaceBundle`, `dataApp.typedSchema` and `dataApp.remove` are gone, with `DataAppCreateInput`. `dataApp.update` takes only `enabled` (`DataAppUpdateInput`).
- `dataApp.list` takes no filter, and `DataAppListFilter` is gone.
- `dataApp.generateSchema`, `dataApp.generateQueries` and `dataApp.generateActions` return the files of an app's repository as `DataAppGeneratedFiles`: its `src/metabase.schema.ts`, and the YAML of the questions and implicit actions its `defineQuery` and `defineAction` exports define (`DataAppGenerateQueriesInput`, `DataAppGenerateActionsInput`, `DataAppQueryDefinition`, `DataAppActionDefinition`).

## 0.1.3

- `dataAction.create` creates an implicit action on a table as well as a query action. `DataActionCreateInput` is a union on `type`: a `"query"` body takes `dataset_query`, an `"implicit"` one takes `kind` (`ImplicitActionKind`, on the barrel) and `table_id`. Neither takes `database_id`, which the server derives from the query.
- `DataActionUpdateInput` patches a query action's `dataset_query` or an implicit action's `kind` and `table_id`, never both, and takes no `database_id`. `dataAction.update` refuses a `table_id` before the request on a server without `dataActionsWithoutModel`, which would drop it unread; `DATA_ACTION_TABLE_GATE` records the gate.
- `DataAction` and `DataActionCompact` read an implicit action's `kind` and `table_id`.
- `DataActionExecuteResult` reads an implicit action's `rows-updated`, `rows-deleted` or `created-row`, and `rows-affected` is optional.

## 0.1.2

- `oauthLogin` takes an optional `signal`. Aborting it, before or during the flow, rejects with the signal's reason when that is a `MetabaseError`, else with an `AbortError` carrying its message, frees the loopback callback port at once, and cancels discovery, client registration or the token exchange in flight. `tryDiscoverMetadata`, `discoverLoginMetadata`, `registerClient` and `exchangeCode` on `@metabase/client/http/oauth` take a signal too, and `@metabase/client/signal` exports `whenAborted`.

## 0.1.1

- `DashboardCreateInput` holds only the fields `POST /api/dashboard` reads, so a layout passed to `dashboard.create` fails to compile; send it as a `DashboardLayoutInput` through `dashboard.update`. At run time `dashboard.create` drops any other key before the request, as the server does, and refuses a blank `name`, as the server does.
- `DashboardLayoutInput` and `DatabaseUpdateInput` are on the barrel.
- `@metabase/client/json-pointer` exports `unescapeJsonPointerSegment`, the inverse of `escapeJsonPointerSegment`.
- `@metabase/client/version/input-gates` exports the input gates recorded on feature-gated body fields, with `gateTriggered` and `inputGatesOf`, and `featureAvailability` says which servers hold a feature.
- `dataAction.update` refuses a `collection_id` before the request on a server without `dataActionCollections`, which would drop it unread.
- `dashboard.get` and `dashboard.update` read a dashboard holding a text, heading or other dashcard bound to no card. The server answers a stub `card` such as `{ query_average_duration: null, download_perms: "none" }` for such a dashcard, which 0.1.0 refused; it reads as `null`, and `dashboardDetailSchema` on the dashboard subpath is the reader.
- A transform's Python `source-tables` entry reads without `database_id` or `schema`, as the server stores an entry whose table or database is gone. `TransformSourceTableEntry` is the stored entry, and `TransformSourceTableEntryInput`, on the barrel, is the entry the create, update and Python test-run bodies take, as strict as before.
- Every transform read on Metabase 59 accepts a Python transform, whose `source-tables` that server keys by alias. `transformRowSchema` and `transformDetailSchema` read it as the list later servers answer, taking each alias from its key; an entry naming its table by id alone reads `database_id`, `schema` and `table` as `null`, and one whose table that server could not find reads `table_id` as `null` too. `transformSourceTablesAsList` is the feature.
- The dependency readers accept the action nodes Metabase 65 adds: `DependencyType` and `DependencyUsageType` take `"action"`, and `DependencyEntityData.type` takes an action's `"implicit"` or `"query"`. `dependency.graph`, `dependency.dependents` and `dependency.broken` explain an older server's refusal of an action as the entity through `actionDependencyGraph`.
- `notification.get`, and the `update`, `archive` and `send` that read through it, refuse a dashboard subscription with the "not a question alert" `ConfigError` instead of a shape error on its payload. `AnyNotification` is the reader: a question alert in full, any other type read no further than `id` and `payload_type`. `CARD_PAYLOAD_TYPE` has the literal type `"notification/card"`.
- `CurrentUser.email` is any string, so `user.current` reads an account whose address Metabase accepts and a stricter email check refuses, such as one with `!` or `/` in the local part or a digit or one-letter top-level domain.
- `transform.create`, `transform.update` and `transformPython.testRun` send a Python source's tables keyed by alias to Metabase 58 and 59, which read no list: a transform entry as its reference less `alias`, which 59 reads and 58, taking only table ids, refuses, or as the bare table id when it names its table by id alone, and a test-run entry as its table id. `TransformSourceTableEntryInput` also takes that id-only entry, `{ alias, table_id }` with `database_id`, `schema` and `table` absent or `null`, so a transform read from 59 updates back unchanged. `pythonTestRun` holds from 58 on a server licensed for Python transforms.
- `SetupInput.user.email` is any string, so `setup.create` hands Metabase an address it accepts and a stricter email check refuses, and the server judges it.
- `collection.itemPages` walks the `trash` alias on every server. No Metabase routes `/api/collection/trash/items`, so the walk reads the trash collection's id from `GET /api/collection/trash` first and pages its items by that id.
- `search.query` and `collection.itemPages` explain an older server's 400 for a `models` value it does not take as the feature it lacks: `measure` in search through `measures`, `transform` through `transforms`, `exploration` through the new `explorations`, and among collection items `measure` through the new `collectionItemMeasures`.
- `collection.itemPages` applies `pinned_state` on Metabase 64 and later, which read it as `pinned-state` and drop the spelling 58 through 63 read.
- `TransformJobUpdateInput.active` records that it needs `transformJobActivation`; a server before 61 drops it unread and still answers the job as active.
- `LibraryPublishTablesInput.collection_id` records that only a server with `tablePublishTargetCollection` (62+) reads it; an older one publishes into its one Library data collection. It is sent on every server.
