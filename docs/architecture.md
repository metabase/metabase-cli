# Architecture

Why the repo is shaped the way it is. The binding rules are in `CLAUDE.md`; this file explains the parts whose rationale is not evident from the code.

## Two packages

A bun workspace. `packages/client` (`@metabase/client`) is the Metabase API client — Zod domain schemas, the HTTP boundary, the OAuth protocol and login flow, the server version model. `packages/cli` (`@metabase/cli`) is the publishable CLI built on it.

The CLI consumes the client as `@metabase/client/<path>` and inlines it at build time through tsdown's `noExternal`, so nothing under `dist/` names the private package. That is why the CLI's manifest never lists it as a dependency.

`zod` is a **peer** dependency of the client, not a normal one. The client's public API is Zod schemas, so the consumer's zod instance is part of the contract — shipping our own copy would hand embedders two incompatible `ZodType` identities.

Root devDependencies hoist and are therefore reachable from the client's source tree. The client's dependency budget (`zod` + `node:` builtins) is a rule to uphold, not something the resolver rejects.

The split is internal. To anyone outside the repo this is the CLI, which is why the root `README.md` is the CLI's user-facing command reference rather than a workspace map, and why `packages/client/README.md` — the client's own reference — is reached only from inside `packages/`. npm renders a README only from the package root, so `packages/cli/README.md` is a pointer to the root one: install, `mb --help`, and the link. The reference itself has one home.

## Resolution: source, not `dist`

`packages/client`'s `exports` map names built output, and `tsdown` emits one `dist/*.js` + `dist/*.d.ts` pair per entry, deriving its entry list from that map — including by globbing `src/domain/*.ts` and `src/resources/*.ts` for the two wildcards. Adding a file to either directory publishes it automatically.

Nothing in this workspace compiles that output. The root `tsconfig.json`'s `paths` sends `@metabase/client/<path>` to `packages/client/src/<path>` for the type-checker, for bun, and for the rolldown pass behind both tsdown builds; `vitest.workspace.ts` carries the same mapping as a `resolve.alias`.

**A tool that consults neither resolves the export map and reads `dist`, which is stale the moment anyone edits the source.** Give a new tool the mapping when you add it — with `dist` present, a lost mapping fails silently rather than loudly.

## What the exports map costs

Because the entry list is derived by globbing, every filename under `domain/` and `resources/` is a published specifier: renaming a file is a breaking change for consumers, and internal helpers in those directories are public whether or not anyone outside imports them. This is a publish-shape decision, not a cleanup — settle it before `private: true` comes off.

## Process state belongs to the CLI

The client never touches `process`. Signals reach it from its caller: `ClientOptions.signal` is composed into every request alongside per-request signals and the timeout, and the package registers no process signal handler.

TLS trust follows the same split. `trustSystemCa()` merges the OS trust store into Node's default CA list so a Metabase behind a corporate proxy or a local development CA verifies without the user setting `NODE_USE_SYSTEM_CA=1`. It mutates global TLS state, which is a CLI's prerogative and not a library's — hence `node:tls` appears nowhere in `packages/client`. An embedder sees Node's bundled CA list unless it opts into more.

The CLI entry owns the only SIGINT handler. It aborts `interruptSignal` so in-flight work unwinds through the error boundary as an `AbortError` (exit 130), and holds a deadline after which the process ends itself at that code — registering any SIGINT listener removes Node's default terminate-on-Ctrl-C.

## Retries are idempotency-aware

GET/HEAD/OPTIONS retry on retryable status codes, network failures and timeouts, and earn one attempt on a fresh socket when the first try hit a pooled connection the peer had already reaped — even with retries disabled.

POST/PUT/PATCH/DELETE retry on none of it. Metabase offers no idempotency-key framework, so a lost connection cannot prove the write never landed, and a resend would double-create. Callers who know an endpoint tolerates a resend opt back in via `idempotent`.

## Pagination invariants

`paginatePages` is the limit/offset iterator over Metabase list endpoints. It yields `Page<T>` (`{ items, total }`) rather than a bare array so the server's count reaches the caller instead of being spent on loop control.

A walk ends on an empty page, on a server count the rows corroborate, or on the caller's `max`. It does **not** end on a short page, which can equally come from a server-side page cap or a filter applied after the limit; and it does not end on a count the rows in hand already exceed, which is a count the server has disproved.

An endpoint returning the same first row at two different offsets is ignoring `offset`. The walk refuses with a `ConfigError` whether or not a count bounds it: a walk that cannot advance either requests forever or serves the same rows twice, and neither is a listing.

At the CLI layer the same principle governs `has_more`. Over-reporting costs one wasted request; under-reporting strands rows the caller can never ask for again. So a count that contradicts the rows in hand is the count that is wrong, and only a source that ran dry may report `has_more: false`.

Truncation by the output byte cap recomputes `has_more` / `next_offset`, making a capped result a resumption point. An envelope pointing the caller back at the offset it just used would livelock an agent, so a window that returned no rows reports no continuation.

## Server versions

The client is built against a window of Metabase majors, `KNOWN_RANGE` in `packages/client/src/version/known-range.ts`, and only the latest patch of each major: patch releases carry fixes, not API-contract changes, so the e2e matrix boots the latest patch per major and that is the whole contract. Inside the window every difference the client cares about is a named feature; outside it the client degrades in one stated way rather than guessing.

**One `ServerProfile`, derived once.** `probeServer` reads `/api/session/properties` into a `ServerInfo` (the version, build date, hash, token-feature map), and `createServerProfile` turns that into the `ServerProfile` the transport carries: the raw facts, `edition` (read from the tag's leading number — `v0.` is OSS, `v1.` is EE — and, for a tag that stamps none, from whether any premium feature is granted, because an unlicensed EE reports the same all-false map OSS does), the derived `features`, and `skew`. A major inside the window is `supported`; one below it keeps its real major as `older-than-known`, so a feature it lacks is named when the server refuses it with a refusal status; one above it is placed at `KNOWN_RANGE.max + 1` as `newer-than-known`. The version is a `ServerVersion`: a `release` with its major and patch, or a `development` build for any tag that names no release (`vUNKNOWN` on head images, `vLOCAL_DEV`, a `-SNAPSHOT` jar). Only an unreleased build reports such a tag, and it is ahead of every release, so a development build is `development`: it passes every rule's `since`, including a rule written for a major not yet released, and is past every `until`. Its token features still gate the premium rules. A persisted probe re-derives its version from the stored tag (`StoredServerVersion`), so a stored record reads the way the placement rules in force place its tag, whatever rules it was written under. The CLI hands the profile record's cached probe to `createClient` as `ClientOptions.server`, so a command pays no probe; a client without one probes lazily on the first call that needs it and memoizes. Nothing may pass a version in — `createClient` takes a profile or probes, never an `assumeVersion` — so the CLI, the harness and the client can never disagree about which server they are on.

**`features.ts` is the only file that compares a major.** `FEATURE_RULES` maps a behaviour name to `{ since, until?, tokenFeature? }`; `evaluateFeatures` turns the placed major and the token map into `Features`, a record of booleans every consumer branches on. Two tests keep the table honest: `major-comparison-guard.test.ts` scans both packages' source and the e2e tier for a `.major` comparison outside the version evaluators, and `features.test.ts` asserts every version-gated rule is non-constant across `KNOWN_RANGE.min … max + 1` and that no name carries a version. When a major leaves the window the rules that stopped flipping fail the second test and are deleted with their wire variants — that is what keeps the switch count bounded. Rules exist for three kinds of consumer: resource methods and readers (`transforms`, `transformTargetTableId`, `libraryChildrenCarryType`), e2e suites that pin per-generation server behaviour (`invalidMbqlIsBadRequest`, `collectionItemsTotalOnEmptyPage`), and skill prose (`boxplotDisplay`, `smartLinkMeasureModel`); a rule no client code reads is still a rule, its consumer is the gate or the skill.

**The server decides; the table explains.** `version/requirements.ts` keys `METHOD_REQUIREMENTS` by `<resource>.<method>` exactly as the method is reached on the client, listing the features it needs strictest first (the first unmet one is what the explanation names, and naming the lowest floor sends a user through one upgrade only to be refused again). The module imports only `FeatureName`, so `--help` reaches it without dragging `domain/` onto the startup chunk. Whether a server grants a feature is the server's fact at request time; a cached profile is a copy from the last probe, and a license activated or a server upgraded since would turn it into a refusal the server never made. So the client sends the request and lets the server answer. Each resource builds `const { explain, explainWalk, refuse, refuseAfterReading } = explainer(transport, "<ns>")` from `version/refusal.ts`, taking the wrappers it uses, and exports its gated methods through `explain(name, method, parameters?)`, visible beside the method's name in the factory's return; `name` is typed as the namespace's own keys, so a key cannot name another method's entry by a typo. `explain` takes a method answering a promise and hands back one with the same signature whose rejection is explained; `explainWalk` takes one answering an async iterable (a `<thing>Pages` walk) and has the failure of any step explained as it is thrown, so a page walk needs no plumbing of its own. `explain-guard.test.ts` fails a gated method a resource exports through anything but exactly one of `explain`, `explainWalk`, `refuse` and `refuseAfterReading` (below), and a wrapped one with no feature to name. When the call fails the way a server rejects what it lacks — a 402 premium refusal (which a gated `/api/ee` prefix answers before routing, whether or not the route exists), an unrouted 404, a 400 on a value outside an older enum or a body an older route reads in another shape, but never a 404 for a missing row, which comes from a route the server serves — `explainRefusal` in `version/refusal.ts` (classifying through `mayBeRefusal` and `explainedFailure`, and needing nothing of the transport but `verifiedServer`) reads a profile the client probed itself (`verifiedServer`, never the one handed in) and, when that profile lacks one of the call's features, throws `CapabilityError` carrying a `RequirementFailure` — `reason`, `detail`, `feature`, `since`, `tokenFeature`, `serverVersion` — and the server's own refusal as its `cause`. A 400 is also an ordinary validation failure, so it counts as the feature's refusal only when nothing in it points elsewhere: when its field errors (`fieldErrors` / `specificFieldErrors`, compared by top-level field) name a field outside the `fields` of the missing parameter features, the server's `HttpError` stands unchanged — a tier-named `data_layer` riding along with another field the server rejects reads as that field's rejection, not the tier floor. A 400 naming no field is the refusal (a v58 table update checks `data_layer` in its model and answers 400 with only a message), and so is any 400 from a server lacking a feature the method itself needs, since the call cannot succeed there whatever field it names (a v59 Python test run rejects the newer `source_tables` shape). The message of a 400-explained refusal quotes the server's answer after the requirement when the server said anything (`HttpError.serverMessage`, its envelope's message or field errors or a plain-text body, is non-null); its field errors stay structured on the cause. A 402 body already names the premium feature, but the refusal is still explained from a probe: only a probe places the server for a version gate, one probe keeps every `RequirementFailure` the same shape, and its write-back corrects the cache the refusal has just shown stale. A server that turns out to have every feature failed for another reason, and its own error stands, as it does when the explaining probe fails. The probe is bounded by its own timeout and cancelled by the client's signal, so an interrupt during it surfaces as the interrupt. The call's features are the method's plus those its arguments bring, parameters first. A parameter's features come from `explain`'s `parameters` callback, a small named function beside the method in its resource file, typed by the method's own arguments and returning `{ feature, fields }` entries: the feature, and the request `fields` the argument travels in as the server names them in a 400. A revision of a measure or a transform (a v58 server answers 404 for the listing and a 400 naming `entity` for a revert), a measure's dependency graph (a 400 naming `type`) and a tier-named `data_layer` (the list filter's 400 names `data-layer`; the update's names nothing) are rejected by an older server, and the rejection names the feature that brought them. A method that needs nothing is not wrapped and never probes, and a wrapped call that needs nothing for the arguments it was handed (a revision of a card) gets its own error back at once, so a baseline command with no cached probe stays socket-free; a `CapabilityError` thrown before the wire passes through `explain` unchanged, since it is no refusal to explain. `requirements.test.ts` asserts the table names exactly the methods the client exposes.

**Refused before the wire only where the server cannot answer.** Some servers take a parameter they do not support and answer as if it had never been sent, rewrite it, or fail it without a cause: a `GET /api/table` filter below its floor lists every table, a search on a server granting `official_collections` but not `content_verification` takes `verified` without applying it (one granting neither answers 402, which the parameter's declaration explains), an import or export before `remoteSyncMerge` ignores `merge`. Such a method refuses first through `transport.requireFeatures` or a value check on `transport.preflightServer()`, never against the cached profile, and says in a comment beside the check what the server would do; those comments are the list. A method every call of which a server without the feature would answer that way — whose whole answer it would misread (`gitSync.syncedCollections`, `gitSync.branch`, `gitSync.trackedBranch`) or whose whole body it would drop (`field.setDataSensitivity`) — is exported through `refuse(name, method)` instead of `explain`, with the comment beside it in the factory's return: `refuse` runs the method's whole `METHOD_REQUIREMENTS` entry through `transport.requireFeatures` before calling it, waiting under the signal of the method's trailing `RequestOptions`, so a method it wraps ends in optional `RequestOptions`. A method answering from a setting the session properties carry is exported through `refuseAfterReading(name, reader, method)` instead (`gitSync.branch`, `gitSync.trackedBranch`): the wrapper reads the properties afresh through `transport.probe(reader, options)`, then checks the method's `METHOD_REQUIREMENTS` entry against the profile that same answer describes, never whichever probe is newest by then, refusing with the `CapabilityError` `transport.requireFeatures` would, so the call costs one request however other calls interleave, and hands the properties to the method, a pure function of them; the exposed method takes only optional `RequestOptions`, whose `signal`, `timeoutMs` and `retries` govern the read. A check that depends on the arguments stays inline in the method. A drop that depends on the patch release rather than the major is judged from the answer instead: `table.update` compares the collection the server answers with the one asked for and, when they differ, throws a `PartialWriteError` (category `partial-write`, not retryable) saying the rest of the update was applied. A `null` the update drops on every server is no value of `TableUpdateInput`. These checks judge by `FEATURE_RULES`, which places a server by its major, so a feature backported to an older patch release, or a rule the table gets wrong, is refused although the server would honour it; nothing finer is possible until Metabase reports its capabilities itself, so the caller may skip them. Every refusal they make, the medallion `data_layer` value check included (a `CapabilityError` whose `RequirementFailure` has reason `superseded-by-feature`: the server has `tableDataLayerTiers`, which takes the medallion names out of its vocabulary), goes through `transport.refuseBeforeSending`, the one place that decides: it throws, unless the client was built with `onPreflightSkipped`, which is then handed the refusal's `CapabilityError` while the call goes on to the server. `requireFeatures` and `refuseAfterReading` hand over every feature a call lacks (`featureFailures`), not only the first, and throw the first when nothing skips. A check reads its profile through `transport.preflightServer()`, which is `verifiedServer()` except under the hook, where a probe failing short of an interrupt is handed over as unverified (`SkippedPreflight` is `{ kind: "refused", refusal }` or `{ kind: "unverified", failure }`) and the call goes on unchecked; `refuseAfterReading` is the exception, since its read is the method's own data and a failed read fails the call. The checks that judge the server's own state rather than a rule (pivoted exports turned off, git-sync's unset or unreadable tracked branch), input the client rejects, the `PartialWriteError` judged from the answer and the explanation of a refusal the server answered never pass through it, and neither does the choice of what to send (git-sync's `expected_branch` and `branch` below). The CLI sets the hook under `--skip-preflight` or `MB_CLI_SKIP_PREFLIGHT=1` and warns once per distinct refusal, and once per run for a server it could not check; without it, its rendering of a `CapabilityError` with no `cause`, which only a refusal before the wire lacks, names the flag. A verified profile is memoized until the client reads the session properties again, so a long-lived embedder whose server gains a license mid-session builds a new client to see it.

**Git-sync sends the tracked branch where an older server ignores it.** Where an older server ignores a key a newer one requires, the key is sent on every server; where an older server acts on it instead, it is sent only where the feature holds. A git-sync import's `expected_branch` is the first kind. When the caller names none, the client reads the tracked branch from the session properties through `transport.probe` and sends it to every server with `remoteSync` whose setting the caller can read and finds set. Only a server with `remoteSyncBranchGuard` rejects an import without it, so only there is an unset setting, or one hidden from a caller who is not an admin, refused before the request; an older server with nothing to read gets none. An export's `branch` is the second kind: an older server reads the setting itself within the request but takes a branch it is sent as a switch, so a branch read a moment earlier would undo a switch another admin made in between. It is sent only to a server with `remoteSync` and `remoteSyncBranchGuard`, which requires it, with the same refusals before the request. Both judge the features by the profile that same read describes (`profileFromProperties` in `version/probe.ts`), and the read settles the verified profile in the same request, so the merge check and the explanation of a refusal that follow cost nothing more. `transport.probe(reader, options)` starts a probe on the probe's own budget (a 10 s timeout, no retries) unless the caller sets `timeoutMs` or `retries`, as `verifiedServer()`'s probe does. The probe every caller shares parses the body as `SessionProperties` only, and the caller's `reader` parses the same body for that caller alone, so a setting one resource requires fails only that resource's call, with the `ResponseShapeError` a read of its own would raise. Probes are ordered by when they started: an answer is applied, made the profile in force and handed to `onServerProbed`, unless a later-started probe has been applied already, so neither goes back to an older answer and an answer outliving a later probe that failed still counts. `verifiedServer()` joins the newest probe started, in flight or settled, and when that one fails the newest applied answer stands in for it. `gitSync.branch` and `gitSync.trackedBranch` cost one read of the session properties: `refuseAfterReading` reads the setting afresh, so a long-lived client sees a branch another admin switched, and checks `remoteSync` against the profile that read describes, because an EE server without the token still shows its admin the setting. A pivoted export reads the `enable-pivoted-exports` setting through `transport.probe` too, so the export's feature checks that follow reuse that read; `exportQuery` on `card` and `dataset` checks the pivot before the byte order mark.

**The CLI declares what a command reaches.** A command declares `requires: readonly MethodKey[] | null`, the methods its body reaches; `commands/requires-guard.test.ts` reads every command file and asserts the declaration equals the `client.<ns>.<method>(` calls in it plus the methods of the helpers it hands the client to — verified, not derived at runtime, because runtime derivation would import the resource layer before `--help`. `defineMetabaseCommand` unions the methods' features for `help --json`, which reports `requires: { methods, features }`; a consumer that wants a floor reads `FEATURE_RULES` for the features named, so no second summary can disagree with the table. The CLI runs no check of its own: the client's explanation reaches the user as the same `CapabilityError` (exit 2).

**Canonical schema, exact wire variants, lossless converters.** The exported domain schema of a resource is the shape the newest supported server returns. Where an older generation answers differently it gets a module-private `<Resource>WireV<N>` schema (N is the first major answering that shape) and a converter to the canonical shape; the feature switch selects deterministically, the transport parses that one schema, and a mismatch is its `ResponseShapeError` naming the expected fields and the tag of the profile in force when the request started, the one the reader was chosen for. There is no guessing between shapes. The canonical field is `nullable`, `null` meaning "this server cannot say"; a converter may add fields but never maps two distinguishable wire states onto one (`job_run_id` — an opaque stub on released servers, a number or `null` on head — becomes `{ started, run_id }`, not `run_id` alone); and a converter strips the wire fields it owns so the JSON the CLI prints is identical on every server. Readers are schema factories the resource hands to `requestParsed` — `transformDetailSchema(features)` / `transformRowSchema(features)` in `domain/transform.ts`, `transformJobRunResultSchema(features)` in `domain/transform-job.ts` — so the exact-schema failure is the transport's and no raw `ZodError` escapes. When the converter needs a second request (`domain/library.ts`: `type` rides the wire from one generation on, `is_remote_synced` is on no generation's wire and comes from the collection listing), the reader tags its generation (`libraryWireSchema(features)`) and a separate exported converter (`toLibrary(wire, listing)`) finishes the job. The pattern to copy is in `domain/transform.ts` and `resources/transform.ts`: `TransformBase` for the fields every generation shares, `Transform` = base plus the newest link, `TransformWireV59Detail` for the hydrated older detail, and the resource doing `const { features } = await transport.server()`, `transport.requestParsed(reader(features), path, opts)`, exported through `explain`. `server()` answers the profile in force — the newest probe the client settled, else the one handed in — and awaits a probe in flight, whose failure falls back to that profile, so a shape read never fails on a probe it did not need. The client keeps one probe: the newest started, shared by every caller while in flight, kept once settled and dropped when it fails; only that one settles the profile in force and reaches `onServerProbed`, so an answer that lands after a later probe started never replaces it.

Two things that look like version drift are not, and must not become switches: a setting's value encoding (a string-typed setting answers bare `text/plain`, everything else `application/json`, and a keyword's bare name under that label is the one body that lies) is dispatched on the value's runtime type by middlewares unchanged since v58, so `parseJsonOrPlain` is a correct sniff; and a resource-missing 404 is `text/plain` `Not found.` on every generation while a route-missing 404 is a JSON string literal, dispatched on which handler produced it, so `isRouteMissingResponse` is a correct sniff too.

**Skew is reported, never refused.** A server above the window runs in the head slot, `KNOWN_RANGE.max + 1`: its additions pass through `.loose()`, and the CLI prints one stderr notice per run, from the cached probe or else the first probe the client runs, pointing at `mb upgrade`; a development build gets no notice, and a server below the window gets one pointing at a Metabase upgrade. A run with no cached probe learns the server only from a probe the client runs, so when its command fails with a failure skew could explain — a shape error or an unrouted 404, never a validation 4xx, a 5xx, a network error, a timeout, a credential failure, a missing row or the CLI's own refusal — `diagnoseFailure` in `commands/runtime.ts` asks the client for `verifiedServer()` on the way out, which costs nothing when the run has probed already and otherwise gives the notice its say; a command that succeeds against an out-of-range server without a cache stays silent. Refusing a newer server would make the CLI unusable against head, which is the build the team lives on. If head has changed a shape the parse fails loudly instead of trying older shapes. Every probe answer the client applies reaches the CLI through `ClientOptions.onServerProbed`, which the client calls without awaiting; the CLI queues a write of the probe to the profile record only when it differs from the cached one in version or granted token features, and before the command ends waits for every probe still in flight (`client.probesSettled()`) and then on the queue, so a probe that outlives a failed command still has its write land before the process exits (a write that fails warns without failing the command). So an explained refusal leaves no stale cache behind for the skills filter or the next run's shape choices, and a run that learns nothing new leaves the profiles file alone. Under the file backend that file also holds OAuth tokens, and every read-modify-write of it within a process runs alone (`exclusively` in `core/auth/storage.ts`), so a probe save never restores a refresh token the server has already rotated away. A record's probe time is when the profile last recorded the server: a login, a listing, or a change. A `ResponseShapeError` whose shape was chosen under the cached profile — its tag is the cached one — earns the same `verifiedServer()` from `diagnoseFailure`: when the fresh probe differs from the cache in version or granted token features, `diagnoseFailure` waits for that probe's write, and the error says the profile was refreshed and, for a read, to retry; for a write it says the request may have been applied and to check before retrying. When the write failed, the error says instead that the profile could not be updated, pointing at the warning that says why, and for a read to retry once that is addressed; for a write, again, to check before retrying. The command is not retried. A shape chosen under a probe the run already settled carries that probe's tag, so its error stands. The one misreading left is a probe settled mid-run with the cached tag but other token features: a shape chosen under it still reads as chosen under the cache, and the error carries a note it did not need. `skills list` / `skills get` filter by the cached probe without a request, and name when the profile last recorded the server and `mb auth list` to probe again whenever they leave a skill out. The cached probe is trusted only when the record's URL is the one the command resolved — `--url` can point a profile name at another host. `auth status` / `auth list` / `auth login` render `skew` beside the version and, in JSON, `edition`, `knownRange` and the `features` map (`core/auth/server-summary.ts`).

**Skills carry `requires`.** Skill prose describes the newest behaviour with no version branches — logic executed by a model is untestable and drifts. A skill declares `requires: [<feature>, …]` in its frontmatter and fences a passage between `<!-- requires: a, b -->` and `<!-- /requires -->`; `mb skills list` / `mb skills get` resolve both against the profile's cached probe (`core/auth/cached-server.ts`, no request), leave out a skill the server cannot use, strip an unmet passage, and report the skipped skills as `unavailable: [{ name, failure }]` with the same `RequirementFailure` a refused command carries. A marker must sit on its own line and never inside a Markdown table, because the formatter splits a table around an HTML comment. Content values an older server stores without complaint — a `boxplot` display, a `table` template tag, a measure smart link — are guarded by these markers only: the client sends them, and nothing refuses them.

**Adding a version-conditional feature** is: a rule in `FEATURE_RULES` named after the behaviour, verified against the reference Metabase checkout's release branches (route files `src/metabase/api_routes/routes.clj` and `enterprise/backend/src/metabase_enterprise/api_routes/routes.clj`; token-feature keys in `src/metabase/premium_features/settings.clj`; trust the source over a branch's committed `openapi.json`, which can lag its routes); the method's entry in `METHOD_REQUIREMENTS`; `requires` on the command; and, where a shape differs per generation, the wire variant and converter. The e2e suite gates with `requireServer(lane, [<feature>])` where a server may lack the route and branches with `serverHas(feature)` where every stack answers and the answers differ.

**When a new Metabase major ships:** raise `KNOWN_RANGE.max`, add the `oss-<N>` / `ee-<N>` stacks to `scripts/e2e-stacks.ts` and `.github/workflows/e2e.yml` and run them — `matrix-coverage.test.ts` fails until every major in the range has both lanes, pinned to an image of its own major and edition — and when a major leaves the window at the other end raise `min` and run the unit tier — `features.test.ts` flags every rule that is now constant, and each one is deleted together with its wire variant, converter, `METHOD_REQUIREMENTS` entries, skill markers and e2e branches. Update the range the root `README.md` states. Nothing else names a major.

## The e2e stack

The suite drives the built binary against a real Metabase in docker compose, with no mocks. `scripts/e2e-matrix.ts` namespaces the compose project and its volumes per stack, so each matrix entry gets its own server, app-db volume, bootstrap artifact and snapshot. `bun run e2e:up` sets no project name and therefore always targets the default stack's containers, whatever `METABASE_CLI_E2E_STACK` says — reach for `e2e:matrix --stack=<id>` when you need a genuinely separate server.

The bootstrap is idempotent and reuses its artifact while the stored key still authenticates, so iteration cost is test execution rather than setup. It refuses to seed a server that already holds seed content, because seeding twice duplicates every entity. The artifact and snapshot are working-tree state while the app-db is a docker volume, so a fresh worktree or a `git clean -x` puts them out of step; `bun run e2e:down && bun run e2e:up && bun run e2e:bootstrap` is the way back.

A green summary reports the lanes that ran. The closing coverage block reports the ones that did not and why — locally, absent an EE license token, that is every `remote_sync`-, `library`- and `content_translation`-gated lane. A gate is `requireServer(lane, [<feature>])`, the same `checkFeatures` the client's explanation runs over the bootstrap's probe, so a lane skips exactly where the server would refuse; `serverHas(feature)` is for a suite that runs on every stack and asserts the outcome its generation produces. ## Generated and vendored files

`packages/cli/src/core/schema/data/` holds the vendored `@metabase/representations` common JSON schemas, written by `scripts/sync-representations.ts` and reaching the CLI only as opaque `import … with { type: "json" }` payloads. The directory is in `.oxfmtrc.json`'s `ignorePatterns`: it is a generated artifact whose writer owns its bytes, and a formatter that reformats it turns every regeneration into a diff the other tool undoes. A generator writing under a formatted tree either emits the formatter's exact output or joins that list.
