# Architecture

Why the repo is shaped the way it is. The binding rules are in `CLAUDE.md`; this file explains the parts whose rationale is not evident from the code.

## Three packages

A bun workspace. `packages/client` (`@metabase/client`) is the Metabase API client — Zod domain schemas, the HTTP boundary, the OAuth protocol and login flow (which the desktop app drives; the CLI never signs in), the server version model. `packages/cli` (`@metabase/rde-cli`) is the `mb` command the RDE desktop app bundles and puts on every agent session's `PATH`. It is private and never published: the app ships `packages/cli/dist/cli.mjs` and `packages/cli/skill-data/`. `packages/desktop` (`@metabase/rde-desktop`) is the Electron app, described under Desktop app below.

The CLI consumes the client as `@metabase/client/<path>` and tsdown's `noExternal` inlines it and every other dependency at build time, so `dist/` imports nothing but `node:` builtins. That is why the CLI's manifest never lists the private package, and why the desktop app can ship `dist/` as a resource with no `node_modules` beside it.

`zod` is a **peer** dependency of the client, not a normal one. The client's public API is Zod schemas, so the consumer's zod instance is part of the contract — shipping our own copy would hand embedders two incompatible `ZodType` identities.

Root devDependencies hoist and are therefore reachable from the client's source tree. The client's dependency budget (`zod` + `node:` builtins) is a rule to uphold, not something the resolver rejects.

The split is internal. To anyone outside the repo this is the CLI, which is why the root `README.md` is the CLI's user-facing command reference rather than a workspace map, and why `packages/client/README.md` — the client's own reference — is reached only from inside `packages/`. The reference itself has one home.

## What the CLI is for

Content is files. A card, dashboard, document, collection, segment, measure, snippet, transform, tag, job or Python library is a YAML file in the user's repository in the representation format, reaches Metabase through remote sync (`mb git-sync import`), and is checked by `mb validate` against the schemas vendored from `@metabase/representations`. The CLI therefore has no `create`, `update`, `archive` or `delete` for any of them, and no export direction: it reads the instance, runs queries and transforms, publishes tables to the Library, extracts database metadata to disk, mints ids, and serves the bundled skills. The one write family is `transform-test`, because the representation format has no file for a transform test yet. `packages/cli/src/commands/surface.ts` is the whole leaf surface; `surface.test.ts` holds the root `help --json` index and the README's command table to it, so a command cannot appear or disappear unnoticed.

## Credentials come from the environment

`core/config.ts` resolves the credential in one order and nothing else. When `MB_AUTH_BROKER` and `MB_AUTH_BROKER_TOKEN` are set, the app's loopback token broker is asked for it (`core/auth-broker.ts`, the CLI's one `fetch` outside the client, allow-listed in `architecture.test.ts`): `GET /v1/credential` with the session token answers `{ url, credential, worktreeId }`, an OAuth access token with its expiry or an API key; a `401` means the session token is bad, a `503 { reason }` that the app is signed out. `MB_URL`, when set, must name the server the broker serves, or the resolution refuses naming both, so a session pointed at one Metabase never sends its token to another. The broker's OAuth grant carries no refresh token — the app keeps that — so the client sees it as a `bearer` credential, and on a Metabase `401` the transport calls the CLI's refresher once, `POST /v1/credential/refresh`, and replays with what comes back. Without a broker, `MB_URL` and `MB_API_KEY` are the developer and e2e path. Without either, every command that reaches a server refuses with one `ConfigError`. The worktree a command acts inside is the grant's `worktreeId` under the broker and `MB_WORKTREE_ID`, a positive integer, without one; the client sends it as `X-Metabase-Worktree-Id` on every request its transport prepares, the version probe included and the OAuth exchange not. The app binds each broker session to its session's worktree and looks it up on every grant, so an agent cannot leave its worktree by changing its environment, and a session whose worktree could not be made gets a `503` instead of the main app. There are no profiles, no keyring, no config directory and no `auth` commands.

The server probe is cached, not the credential. `core/server-cache.ts` keeps one `/api/session/properties` probe per server URL under `$XDG_CACHE_HOME/metabase-rde/` for an hour, so a session of many `mb` calls pays one probe; a gated command with nothing cached probes once and stores the answer, a baseline command never probes, and `mb skills` resolves the connected server the same way.

## Resolution: source, not `dist`

`packages/client`'s `exports` map names built output, and `tsdown` emits one `dist/*.js` + `dist/*.d.ts` pair per entry, deriving its entry list from that map — including by globbing `src/domain/*.ts` and `src/resources/*.ts` for the two wildcards. Adding a file to either directory publishes it automatically.

Nothing in this workspace compiles that output. The root `tsconfig.json`'s `paths` sends `@metabase/client/<path>` to `packages/client/src/<path>` for the type-checker, for bun, and for the rolldown pass behind both tsdown builds; `vitest.workspace.ts` carries the same mapping as a `resolve.alias`.

**A tool that consults neither resolves the export map and reads `dist`, which is stale the moment anyone edits the source.** Give a new tool the mapping when you add it — with `dist` present, a lost mapping fails silently rather than loudly.

## What the exports map costs

Because the entry list is derived by globbing, every filename under `domain/` and `resources/` is a published specifier: renaming a file is a breaking change for consumers, and internal helpers in those directories are public whether or not anyone outside imports them. This is a publish-shape decision, not a cleanup — settle it before `private: true` comes off.

## Process state belongs to the CLI

The client never touches `process`. Signals reach it from its caller: `ClientOptions.signal` is composed into every request alongside per-request signals and the timeout, and the package registers no process signal handler.

TLS trust follows the same split. `trustSystemCa()` merges the OS trust store into Node's default CA list so a Metabase behind a corporate proxy or a local development CA verifies without the user setting `NODE_USE_SYSTEM_CA=1`. It mutates global TLS state, which is a CLI's prerogative and not a library's — hence `node:tls` appears nowhere in `packages/client`. An embedder sees Node's bundled CA list unless it opts into more.

The CLI entry owns the only SIGINT handler. It aborts `interruptSignal` so in-flight work unwinds through the error boundary as an `AbortError` (exit 130), and holds a deadline after which the process ends itself at that code — registering any SIGINT listener removes Node's default terminate-on-Ctrl-C.

## Retries are idempotency-aware

GET/HEAD/OPTIONS retry on retryable status codes, network failures and timeouts, and earn one attempt on a fresh socket when the first try hit a pooled connection the peer had already reaped — even with retries disabled.

POST/PUT/PATCH/DELETE retry on none of it. Metabase offers no idempotency-key framework, so a lost connection cannot prove the write never landed, and a resend would double-create. Callers who know an endpoint tolerates a resend opt back in via `idempotent`.

## Pagination invariants

`paginatePages` is the limit/offset iterator over Metabase list endpoints. It yields `Page<T>` (`{ items, total }`) rather than a bare array so the server's count reaches the caller instead of being spent on loop control.

A walk ends on an empty page, on a server count the rows corroborate, or on the caller's `max`. It does **not** end on a short page, which can equally come from a server-side page cap or a filter applied after the limit; and it does not end on a count the rows in hand already exceed, which is a count the server has disproved.

An endpoint returning the same first row at two different offsets is ignoring `offset`. The walk refuses with a `ConfigError` whether or not a count bounds it: a walk that cannot advance either requests forever or serves the same rows twice, and neither is a listing.

At the CLI layer the same principle governs `has_more`. Over-reporting costs one wasted request; under-reporting strands rows the caller can never ask for again. So a count that contradicts the rows in hand is the count that is wrong, and only a source that ran dry may report `has_more: false`.

Truncation by the output byte cap recomputes `has_more` / `next_offset`, making a capped result a resumption point. An envelope pointing the caller back at the offset it just used would livelock an agent, so a window that returned no rows reports no continuation.

## Server versions

The client is built against a window of Metabase majors, `KNOWN_RANGE` in `packages/client/src/version/known-range.ts`, and only the latest patch of each major: patch releases carry fixes, not API-contract changes, so the e2e matrix boots the latest patch per major and that is the whole contract. Inside the window every difference the client cares about is a named feature; outside it the client degrades in one stated way rather than guessing.

**One `ServerProfile`, derived once.** `probeServer` reads `/api/session/properties` into a `ServerInfo` (parsed tag, build date, hash, token-feature map), and `createServerProfile` turns that into the `ServerProfile` the transport carries: the raw facts, `edition` (read from the tag's leading number — `v0.` is OSS, `v1.` is EE — and, for a tag that stamps none, from whether any premium feature is granted, because an unlicensed EE reports the same all-false map OSS does), the derived `features`, and `skew`. A major inside the window is `supported`; one below it keeps its real major as `older-than-known`, so every feature it lacks is refused by name; one above it is placed at `KNOWN_RANGE.max + 1` as `newer-than-known`; a tag that does not parse — head images report `vUNKNOWN`, local builds `vLOCAL` or a `-SNAPSHOT` — is `unknown` and has no major at all, so no version bound refuses it and only a missing token feature can. The CLI hands the cached probe to `createClient` as `ClientOptions.server`, so a command pays no probe; a client without one probes lazily on the first call that needs it and memoizes. Nothing may pass a version in — `createClient` takes a profile or probes, never an `assumeVersion` — so the CLI, the harness and the client can never disagree about which server they are on.

**`features.ts` is the only file that compares a major.** `FEATURE_RULES` maps a behaviour name to `{ since, until?, tokenFeature? }`; `evaluateFeatures` turns the placed major and the token map into `Features`, a record of booleans every consumer branches on. Two tests keep the table honest: `major-comparison-guard.test.ts` scans both packages' source and the e2e tier for a `.major` comparison outside the version evaluators, and `features.test.ts` asserts every version-gated rule is non-constant across `KNOWN_RANGE.min … max + 1` and that no name carries a version. When a major leaves the window the rules that stopped flipping fail the second test and are deleted with their wire variants — that is what keeps the switch count bounded. Rules exist for three kinds of consumer: resource methods and readers (`transforms`, `transformTargetTableId`, `libraryChildrenCarryType`), e2e suites that pin per-generation server behaviour (`invalidMbqlIsBadRequest`, `collectionItemsTotalOnEmptyPage`), and skill prose (`boxplotDisplay`, `smartLinkMeasureModel`); a rule no client code reads is still a rule, its consumer is the gate or the skill.

**Every method declares what it needs and refuses before the wire.** `version/requirements.ts` keys `METHOD_REQUIREMENTS` by `<resource>.<method>` exactly as the method is reached on the client, listing the features it needs strictest first (the first unmet one is what the refusal names, and naming the lowest floor sends a user through one upgrade only to be refused again). Each resource method opens with `await transport.require(key)`; a method whose list is empty returns at once and never probes, so a baseline command with no cached probe stays socket-free. Otherwise the transport reads the profile and throws `CapabilityError` carrying a `RequirementFailure` — `reason`, `detail`, `feature`, `since`, `tokenFeature`, `serverVersion` — before any request. A rule bounded by `until` normally describes a shape only older servers had and may not be required, since the refusal would name a floor the server is above; the one kind that may is a route later releases removed, whose refusal reads `version-too-new` and names the range instead. `requirements.test.ts` asserts the literal `require("…")` set in `resources/` equals the table. A parameter only some supported servers honour (an older listing drops a filter it does not know without a word) is a floor the method table cannot express, so the method maps that parameter to a feature and asks `transport.requireFeatures` for it beside its own key; both surfaces share one check and one refusal. `ClientOptions.enforceRequirements: false` is the escape hatch; the CLI wires `--skip-preflight` / `MB_CLI_SKIP_PREFLIGHT=1` to it, and a version-selected reader then still costs one lazy probe because the wire shape is chosen from the profile. The module imports only `FeatureName`, so the CLI's preflight and `--help` reach it without dragging `domain/` onto the startup chunk.

**The CLI's preflight asks the client.** A command declares `requires: readonly MethodKey[] | null`, the methods its body reaches; `commands/requires-guard.test.ts` reads every command file and asserts the declaration equals the `client.<ns>.<method>(` calls in it plus the methods of the helpers it hands the client to — verified, not derived at runtime, because runtime derivation would import the resource layer before `--help`. `defineMetabaseCommand` unions the methods' features, and `createPreflightEnforcer` runs once per command: `client.server()` (cached or one live probe), `checkFeatures`, and the same `CapabilityError` (exit 2) the client would raise moments later. A probe that fails ends the command with that network error rather than warning and proceeding, which would only buy a second connection attempt and the same error. `help --json` reports `requires: { methods, features }`; a consumer that wants a floor reads `FEATURE_RULES` for the features named, so no second summary can disagree with the check.

**Canonical schema, exact wire variants, lossless converters.** The exported domain schema of a resource is the shape the newest supported server returns. Where an older generation answers differently it gets a module-private `<Resource>WireV<N>` schema (N is the first major answering that shape) and a converter to the canonical shape; the feature switch selects deterministically, the transport parses that one schema, and a mismatch is its `ResponseShapeError` naming the server tag and the expected fields. There is no guessing between shapes. The canonical field is `nullable`, `null` meaning "this server cannot say"; a converter may add fields but never maps two distinguishable wire states onto one (`job_run_id` — an opaque stub on released servers, a number or `null` on head — becomes `{ started, run_id }`, not `run_id` alone); and a converter strips the wire fields it owns so the JSON the CLI prints is identical on every server. Readers are schema factories the resource hands to `requestParsed` — `transformDetailSchema(features)` / `transformRowSchema(features)` in `domain/transform.ts`, `transformJobRunResultSchema(features)` in `domain/transform-job.ts` — so the exact-schema failure is the transport's and no raw `ZodError` escapes. When the converter needs a second request (`domain/library.ts`: `type` rides the wire from one generation on, `is_remote_synced` is on no generation's wire and comes from the collection listing), the reader tags its generation (`libraryWireSchema(features)`) and a separate exported converter (`toLibrary(wire, listing)`) finishes the job. The pattern to copy is in `domain/transform.ts` and `resources/transform.ts`: `TransformBase` for the fields every generation shares, `Transform` = base plus the newest link, `TransformWireV59Detail` for the hydrated older detail, and the resource doing `await transport.require(key)`, `const { features } = await transport.server()`, `transport.requestParsed(reader(features), path, opts)`.

Two things that look like version drift are not, and must not become switches: a setting's value encoding (a string-typed setting answers bare `text/plain`, everything else `application/json`, and a keyword's bare name under that label is the one body that lies) is dispatched on the value's runtime type by middlewares unchanged since v58, so `parseJsonOrPlain` is a correct sniff; and a resource-missing 404 is `text/plain` `Not found.` on every generation while a route-missing 404 is a JSON string literal, dispatched on which handler produced it, so `isRouteMissingResponse` is a correct sniff too.

**Skew is reported, never refused.** A server above the window runs in the head slot, `KNOWN_RANGE.max + 1`: its additions pass through `.loose()`, and the CLI prints one stderr notice per run; an unparseable tag gets its own notice, and a server below the window gets one pointing at a Metabase upgrade while its commands are refused one feature at a time. Refusing a newer server would make the CLI unusable against head, which is the build the team lives on. If head has changed a shape the parse fails loudly instead of trying older shapes. A `ResponseShapeError` or a `CapabilityError` raised under a cached probe earns one re-probe (`refreshProbeOnStaleError` in `commands/runtime.ts`): a server whose version tag or granted token features changed since the cache was written — an upgrade that changed a shape, or an upgrade or new licence that clears a floor the refusal still names — has its cache entry rewritten and the error says so; the command is not retried, because its request may have been a write. The cache is keyed by the server URL, so a probe of one server is never read for another (`core/server-summary.ts` phrases the notices).

**Skills carry `requires`.** Skill prose describes the newest behaviour with no version branches — logic executed by a model is untestable and drifts. A skill declares `requires: [<feature>, …]` in its frontmatter and fences a passage between `<!-- requires: a, b -->` and `<!-- /requires -->`; `mb skills list` / `mb skills get` resolve both against the connected server (`core/skill-server.ts`: the cached probe, or one probe stored for the processes that follow; without a credential or a reachable server nothing is filtered and the notice says why), leave out a skill the server cannot use, strip an unmet passage, and report the skipped skills as `unavailable: [{ name, failure }]` with the same `RequirementFailure` a refused command carries. A marker must sit on its own line and never inside a Markdown table, because the formatter splits a table around an HTML comment.

**Adding a version-conditional feature** is: a rule in `FEATURE_RULES` named after the behaviour, verified against the reference Metabase checkout's release branches (route files `src/metabase/api_routes/routes.clj` and `enterprise/backend/src/metabase_enterprise/api_routes/routes.clj`; token-feature keys in `src/metabase/premium_features/settings.clj`; trust the source over a branch's committed `openapi.json`, which can lag its routes); the method's entry in `METHOD_REQUIREMENTS`; `requires` on the command; and, where a shape differs per generation, the wire variant and converter. The e2e suite gates with `requireServer(lane, [<feature>])` where a server may lack the route and branches with `serverHas(feature)` where every stack answers and the answers differ.

**When a new Metabase major ships:** raise `KNOWN_RANGE.max`, add the `oss-<N>` / `ee-<N>` stacks to `scripts/e2e-stacks.ts` and `.github/workflows/e2e.yml` and run them — `matrix-coverage.test.ts` fails until every major in the range has both lanes, pinned to an image of its own major and edition — and when a major leaves the window at the other end raise `min` and run the unit tier — `features.test.ts` flags every rule that is now constant, and each one is deleted together with its wire variant, converter, `METHOD_REQUIREMENTS` entries, skill markers and e2e branches. Update the range the root `README.md` states. Nothing else names a major.

## Desktop app

`packages/desktop` (`@metabase/rde-desktop`) is the Electron app, a private workspace member that is built by electron-vite into `out/` and never published. It has three compile targets over the root `tsconfig.json`: `tsconfig.node.json` covers `src/main`, `src/preload`, `src/contracts` and `scripts`; `tsconfig.web.json` covers `src/renderer` and `src/contracts` with the DOM lib. Its unit tests are the `desktop` vitest project, so the root `check` reaches its typecheck, lint, format and tests, and `bun run build:desktop` builds the client, the CLI and the app in that order. Main and preload bundle every dependency (`externalizeDeps: false`) because the packaged app ships `out/` alone and a sandboxed preload cannot load from `node_modules`. `electron-builder.yml` packages that `out/` with no `node_modules` into an AppImage, a dmg and an NSIS installer, and copies the CLI's `dist/`, its `skill-data/` and the two static `mb` shims (`mb` for a POSIX shell, including Git Bash on Windows, and `mb.cmd` for the Windows command processor) to `resources/rde-cli/`, where `main/cli/paths.ts` finds them through `process.resourcesPath`. `main/updates.ts` drives electron-updater: a check on launch and every six hours, a download only when the user asks for it, and the state pushed to the renderer's toast over `updates.state`; it stays off under `RDE_TEST_MODE` and in a build that cannot replace itself, and `RDE_UPDATE_FEED` names a generic feed, which is how `scripts/release-smoke.ts` offers the AppImage under test to itself as a newer version.

The process model: the main process owns the window, the lifecycle and every capability that touches the machine, and answers IPC requests after parsing each payload with the channel's zod schema from `src/contracts/ipc.ts`. The preload runs sandboxed with context isolation and exposes one object, `window.rde`, whose methods are the channels of that contract and nothing else, so the page never sees `ipcRenderer`. A failed call reaches the page as an `IpcRemoteError` carrying the message main threw, without Electron's framing or the error's class. The renderer is a plain React document that reads `window.rde` through `src/renderer/bridge.ts` and cannot reach Node, the file system or the network beyond its own `file:` origin (the CSP in `index.html` allows `'self'` only). Because that CSP withholds `unsafe-eval`, `renderer/zod-setup.ts` runs before the first schema is built and stops Zod probing for the `Function` constructor, a refusal Chromium would otherwise report as an error on a page that is working. It also installs Zod's English messages, since the bundle drops the side effect that would.

The window has no native title bar; the app's own top strip is the title bar. `main/window.ts` alone decides it per platform. On macOS the window uses `hiddenInset` with the traffic lights centred on the strip in its leading corner. On Windows and Linux it uses the window controls overlay, drawn transparent over the strip's trailing corner with its buttons in the active theme's ink, and a theme change recolours them. A native frame there would add a second title bar and a menu above the app's own strip. The window is shown at once over the `--page` colour rather than held until `ready-to-show`, because a hidden window with the overlay can stop drawing frames on X11 until it is resized. The renderer learns which corner is taken from `window.chrome`, a `WindowChrome` from `contracts/window.ts`. `renderer/chrome.ts` turns that value into two CSS insets: the traffic lights' width, or the overlay's width read from Chromium's `titlebar-area-*` variables. Every column opens with a `WindowStrip` (`components/ui/window-strip.tsx`), 48 px tall, the height main gives the overlay and centres the lights on. A strip is a drag region, every control inside it opts out in `renderer/chrome.css`, and the strip at a window edge pads itself clear of the operating system's buttons. A closed side panel takes no width: its toggle moves into the main area's strip through the `TrailingCorner` context, so the strip that reaches the trailing edge pads for the overlay and the toggle keeps the spot it had on the open panel's strip.

The sidebar and the side panel are as wide as a person drags them. `contracts/layout.ts` holds the `PanelLayout` stored in the settings record, each column's minimum, initial and maximum width, and the main area's minimum; the window's minimum width is the three minimums together. The record keeps what was chosen, and `renderer/layout.ts` fits it to the window on every render: each column within its bounds, and when the three do not fit, the side panel gives way to its minimum first and the sidebar after it, so a wider window shows the chosen widths again. A handle (`components/ui/resize-handle.tsx`) sits on each column's inner edge as a focusable `separator` whose value is the width. Arrow keys move it, Home and End take it to either end, and a double-click returns the column to its initial width. `renderer/panels.ts` gives the columns their widths as CSS variables on the shell's root. A drag moves those variables directly, so nothing under the shell renders while the pointer moves, and the layout is committed and saved once, when the pointer lets go. A container that measures its own content, the timeline and the diff, carries `SETTLES_ON_RESIZE`; for the length of a drag it keeps the width it had when the drag began, so its rows are measured once when the drag ends instead of on every pixel.

What main owns, and what the renderer is told. `main/settings/store.ts` holds one zod-parsed `settings.json` under `app.getPath("userData")`, written through a temporary file and a rename, with a migration per file generation. A change is a function of the current settings, and the store applies changes one at a time, each over what the last one wrote, so a burst from different callers lands whole and in order. The Metabase credential inside it is a `safeStorage` blob that only `main/auth/secret.ts` opens; `main/auth/refresh.ts` is the single place the connection changes state, moving to `signed-out` when a token cannot be renewed and to `stale` when Metabase cannot be reached; every change is pushed to the window on `connection.state`, so the sidebar and the Metabase panel follow a sign-out mid-session, and the reason it carries is written for a person, with the server's own error in the main log. `main/auth/broker.ts` listens on a loopback port for the life of the process and hands a session's child processes a short-lived credential for the connected instance, answering the `/v1/` contract `packages/cli/src/core/auth-broker.ts` parses; the refresh token never appears in a response. `main/providers/` resolves each agent binary on the login shell's `PATH`, reads its version and asks its own health probe, and `main/providers/<kind>/` is the only place that knows what a provider is. The renderer sees none of this: it reads a `SettingsView` with no credential and a `ServerSummary` that carries the version, the edition and the three capabilities the app depends on, rather than the client's own server profile.

A session is the provider's work turned into one vocabulary. `contracts/events.ts` holds `SessionEvent`, seventeen kinds over a session-scoped envelope, with the turn-scoped kinds carrying the turn they belong to. An adapter produces those events and nothing else produces them, so the renderer never sees a provider's own message. `main/providers/adapter.ts` is the interface: a probe, a `start` that returns a session with `sendTurn`, `answer`, `interrupt` and `stop`, the native id a later resume takes, and a `rewind` that cuts the provider's own conversation back to just before a prompt or says it cannot. The session takes its clock and event-id source from the caller, which is what lets a replay test assert an exact sequence off a recorded stream.

Claude Code runs through `@anthropic-ai/claude-agent-sdk`: one `query()` per session over a prompt queue, so every turn reaches the same process, with permissions and questions answered through its `canUseTool` callback. Codex runs through `codex app-server`, a newline-delimited JSON-RPC dialogue over the child's stdio that `main/providers/codex/client.ts` frames and correlates; approvals and user input arrive as the server's own requests and are answered by id. Each provider directory holds its wire schemas, the state machine that maps the stream onto events, the shaping of the asks a person answers, and the session itself. `main/providers/text.ts` holds the three helpers both need. `scripts/record-provider.ts` runs one small real session per provider and writes the raw frames under that provider's `fixtures/`, which the mapping tests replay.

A session is an append-only log and a fold over it. `sessions/<id>/events.jsonl` under `app.getPath("userData")` is the record; `contracts/projector.ts` is the pure fold from those events to the `SessionSnapshot` the renderer renders, and the same function runs in main to hold the live snapshot and in the renderer to apply the batches main pushes. `main/sessions/engine.ts` is the decider: it validates a command against the current snapshot, appends the events, advances the snapshot and publishes the batch, and the provider turn, the worktree and the checkpoint are reactions to what is already written. `main/sessions/live.ts` holds one session's running state, serialising its writes and coalescing its pushes to a frame. A session reopened after a crash closes what the killed run left open: every request that was still waiting resolves as expired, and a turn that was running completes as interrupted.

What the renderer draws is decided before a component sees it. `renderer/timeline/rows.ts` folds the snapshot's flat items into the rows the transcript shows: a stretch of tool calls inside one turn reads as one activity row, a settled turn's work collapses behind a fold the reader can open, a turn cut short says so, and a running session ends in exactly one working row. `renderer/markdown/blocks.ts` splits a message into the Markdown blocks the agent has finished and the one it is still writing, and decides nothing on a half-typed last line, so a delta reparses only the tail while every finished block keeps the element it already rendered. `renderer/timeline/follow.ts`, `renderer/composer/triggers.ts`, `renderer/composer/choices.ts`, `renderer/session-list.ts`, `renderer/pulse.ts` and `renderer/keybindings.ts` are the same shape: pure modules with their own tests, over which the components render. The transcript is a `@legendapp/list` with the browser's own scroll anchoring switched off, so rows arriving at the end never move what the reader is looking at; following the live edge stops on a gesture away from it rather than on a position, because a list pinned to the end produces no scroll event that could arm it again. The composer leads with its text field and keeps one row under it. For a new session `renderer/composer/choices.ts` resolves what it will start on and gives each choice its own chip, which shows the current value and opens a menu: where it runs, the agent when more than one is ready, the model and the permissions. A lone agent heads the model's menu instead of taking a chip. The model chip always names a real model from the agent's own list, which main reads from the agent at detection (the Claude SDK's handshake, Codex's `model/list`) and keeps a written-down list for only when the agent cannot answer. Which model and which permissions a new session starts on are settings in Settings › Agents; a pick in the composer holds for that session alone. On a short row the workspace drops to its icon and the chevrons go before any label truncates. The permissions are ask first, allow edits, auto (the agent's own reviewer decides each ask: Claude's `auto` mode, Codex's `auto_review`) and skip every check. A running session shows the agent, the model's label and the permissions as one line of text, and the same round button sends a message or stops the turn. The text field keeps the focus through a send, including the first, where the session's field replaces the new-session one. Tokens live in `renderer/tokens.css`, primitives in `components/ui/` and `components/agent/`, composites in `components/`, and `THIRD_PARTY_NOTICES.md` carries the license notice for the copied code, the tokens and most of `components/agent/`.

Git runs through `main/git/service.ts` and nothing else names the binary. Reads carry `--no-optional-locks` so a checkout the user has open elsewhere is not raced for its index; writes fsync the objects and refs they publish, because a rename without one can leave a zero-byte ref that every later fetch trips over; every diff names its own prefixes and refuses the configured external differs, so a user's git configuration cannot change what the app parses. A worktree session gets `git worktree add -b rde/<slug> <root>/<slug> <base>` under the configured worktree root, with the slug taken from the first prompt and de-duplicated against the branches and directories already there. A checkpoint is the checkout's tree captured through a private index beside the real one and published as `refs/rde/checkpoints/<session>/<seq>`, so the user's branch gains no commit and their staging area is untouched; capture runs after the turn is recorded and never extends it.

The Changes panel asks main for a diff and renders what comes back. A turn's diff runs between the checkpoint before it and its own; the session's whole diff runs from the baseline checkpoint to a tree of the checkout written through a private index the way a checkpoint is, so files the agent created and never staged are in it and ignored ones are not. `main/sessions/changes.ts` answers the panel: each file's change kind and counts beside one patch, a whole-file context on request, a file reverted to the checkpoint the view starts from through `git restore --worktree` so the user's index is untouched, the branch's standing against its upstream and its base, a commit, a push whose output streams to the renderer as git prints it, and the pull request page for a GitHub or GitLab remote. The renderer parses the patch into one virtualised `@pierre/diffs` list highlighted in a worker, beside a `@pierre/trees` file tree; what it shows, the turn a view names, what a revert returns a file to and whether commit or push can run, is decided in `renderer/changes/`. The panel's head is two rows at every width it allows: a quiet line with the branch and how it stands against its upstream or its base, then the turn switch and a menu of diff options beside the one action the branch is waiting for. `branchActions` picks that action (commit while the checkout has changes, push while the remote lacks a commit, the pull request once it has them all) and puts the other two in a menu, each with what stops it. Editing from a prompt appends `session.rewound`: the fold drops that turn and every one after it, a worktree session can return its files to the checkpoint before it, and the provider forks its conversation just before the prompt, which works for Claude Code because the app gives every prompt the UUID the SDK records it under. A provider that cannot rewind starts a new conversation handed the transcript up to that point. Anything the app would give the operating system, a URL for the browser or a file for the editor, goes through `main/external.ts`, and under `RDE_TEST_MODE` it is recorded for the drivers instead.

The Files tab beside it shows the session's checkout as it stands: what git tracks and the new files it does not ignore, less those deleted from disk, with the session's changes marked on the same tree component. `SessionChanges.tree` and `.preview` answer it. A preview is read in main with a byte limit, a binary test and a symlink kept inside the checkout, and comes back as a union the renderer cannot mistake: text, binary, too large, or gone. Text renders read-only through the diff's highlighter. The tab opens a file in the editor through the same channel as the Changes panel and mentions it in the session's composer. Nothing in the app edits a file; the agent does, and the person reviews it in Changes.

Metabase work in a session goes through the bundled `mb`, for the agent and for the app alike. `main/cli/paths.ts` finds the CLI: the workspace's `packages/cli/dist/cli.mjs` and `skill-data/` in development, `resources/rde-cli/` in a packaged app. Every provider process starts with the `mb` shim from `resources/rde-cli/bin/` first on its `PATH`, the broker's `MB_URL` and token, and `MB_SKILLS_DIR`. The shim runs the CLI on the app's own executable with `ELECTRON_RUN_AS_NODE` set for that one child, so the agent's Node is never involved. The first turn and every resume carry `main/sessions/brief.ts`, a system-prompt block under two hundred words that names the checkout, the `mb db` and `mb table` commands the schema is read through, `mb skills get core` and the import command; the skills carry the method. The Metabase panel reads the same CLI through `main/cli/runner.ts`, which runs one command under a broker session of its own and parses its JSON. It reads a failure from the error envelope the CLI prints off a terminal, so a refusal reaches the panel in the CLI's own words. A command that reports its own failure in its answer, `validate` or a waited `transform run`, is read through `report`, which takes the answer on the CLI's failure exit too. `main/metabase/loop.ts` answers the panel. On an instance that offers remote sync it reads the branch Metabase is synced to, its running or last task with its progress, the objects edited in Metabase that git lacks (`git-sync dirty`) and whether the remote moved past it (`git-sync has-remote-changes`); on one that does not, it asks nothing. It finds whether the checkout's `.gitignore` still lacks `.scratch/`, and runs **Sync to Metabase**. `main/metabase/readiness.ts` decides whether a sync can run: it needs a connection that offers remote sync, a branch, a clean checkout, an origin remote and no upstream commits the branch lacks. Importing the branch the instance tracks needs a confirmation. A sync pushes the branch when origin lacks it, runs `mb git-sync import`, and appends `sync.completed` with the server's message or with links to the objects the branch changed that Metabase gives a page. `main/metabase/content.ts` lists the session's content: every YAML the session changed under the content roots, read as the object its last `serdes/meta` entry names (`main/metabase/links.ts`), checked in one `mb validate`, translated in one `mb eid` so an object Metabase holds opens there, and, for a transform Metabase holds, its last run from `mb transform get`. `main/metabase/transforms.ts` runs a transform with `mb transform run --wait` and its tests one after another with `mb transform-test run`. What the panel shows of all this is decided in `renderer/metabase/panel.ts`: the head names the host, the version and the user and links to the instance, a capability the instance lacks appears only as the reason an action is off, and the panel reads Metabase again every two seconds while a task runs.

`src/architecture.test.ts` holds the layering to that shape: `ipcRenderer` only in the preload, `window.rde` only in the renderer's bridge, Electron's registrar and the folder picker only in the composition root, `child_process` only in `main/process/spawn.ts`, `safeStorage` only in `main/auth/secret.ts`, the git binary only in `main/git/service.ts`, the session log's file name only in `main/sessions/log.ts`, the projector only in the renderer's own session store, the virtualised list only in the timeline that owns the scroll, the Markdown parser only in the one component that runs it, the diff viewer and the file tree each in the one component that renders it, Electron's shell only in the composition root, the title bar options only in `main/window.ts`, no drag region outside `renderer/chrome.css`, the CLI's entry and `ELECTRON_RUN_AS_NODE` only in `main/cli/paths.ts`, an arbitrary Tailwind length only in `components/ui/`, no text size outside the type scale in `tokens.css` and no class merge that does not know its steps, no colour written as a hex literal, no `/api/` path anywhere, and provider names only in the contract and under `main/providers/`.

Playwright's Electron driver is the headless proof: `scripts/smoke.ts` launches `out/` under `xvfb-run`, waits for the theme attribute the renderer sets once main has answered, asserts the title and an error-free console, screenshots into `RDE_EVIDENCE_DIR`, and verifies that quitting leaves no child process behind. `scripts/drive.ts <scenario>` acts through the UI for a whole flow, taking the channels under `RDE_TEST_MODE` for what a person would do outside the window: answering the folder picker, minting and revoking a broker session. Its scenarios live in `scripts/scenarios/`, one file per flow, over the helpers in `scripts/scenario.ts`. The `desktop-e2e` vitest project runs every scenario in turn, and `bun run check:e2e` builds the app and runs that project under `xvfb-run`. A scenario that needs what the machine lacks, a licence with remote sync or a packaged build, carries a gate that reports its lane as skipped with the reason, never as a pass. The `chrome` scenario starts `xfwm4` on the display and moves the X pointer through XTEST (`scripts/x-pointer.py`), because Playwright's input reaches the page below the window system and never meets a drag region; it drags the window by the strip, clicks controls inside it, maximises the window with a double-click and checks that no control sits under the overlay. The `type` scenario weighs every visible character of Settings, the sidebar, a running session, a permission ask and both side-panel tabs by its computed size, in both themes, and fails a surface where under half of its text renders at the body size or any renders under 12 px. The `settings-screen` scenario checks that Settings fills the window with only the section a checklist step, the palette or the section list names, and that Back to app and the new-session chord leave it, shooting each section in both themes. The `composer-states` scenario shoots the composer for a new session, an open request, an idle session and a running turn, in both themes at the default and the minimum window width, and fails when its controls take a second row or reach past its edge. It also walks the controls with Tab, picks from a chip with the arrow keys, and sends with Enter and with the send-and-keep-drafting chord. The `resize` scenario drags each column's handle with a `ResizeObserver` on the held containers and the timeline's rows, and fails if any row, or any held container's width, changes while the pointer moves. It also narrows the window to its minimum and widens it again, relaunches and reads the same widths back, and resets one column by double-click and moves the other by keyboard. `scripts/recorder.ts` captures the Xvfb screen with `ffmpeg` and re-times the clip against the wall clock. `scripts/record.ts` runs a whole scenario under it as `<unit>-<scenario>.mp4` and reports the clip's real duration, which is what a review gate reads, and a scenario whose setup outlasts the clip records only its own segment. `scripts/oauth-check.ts` drives the OAuth grant against a live Metabase, logging what discovery answered, and refuses out loud on a server that offers no scope the app can use; it and the `oauth-connect` scenario approve the grant on Metabase's own consent page through `scripts/consent.ts`, which signs the admin in and ticks the full-access scope in a headless Chromium.

## The e2e stack

The suite drives the built binary against a real Metabase in docker compose, with no mocks. `scripts/e2e-matrix.ts` namespaces the compose project and its volumes per stack, so each matrix entry gets its own server, app-db volume, bootstrap artifact and snapshot. `bun run e2e:up` sets no project name and therefore always targets the default stack's containers, whatever `METABASE_CLI_E2E_STACK` says — reach for `e2e:matrix --stack=<id>` when you need a genuinely separate server.

The bootstrap is idempotent and reuses its artifact while the stored key still authenticates, so iteration cost is test execution rather than setup. It refuses to seed a server that already holds seed content, because seeding twice duplicates every entity. The artifact and snapshot are working-tree state while the app-db is a docker volume, so a fresh worktree or a `git clean -x` puts them out of step; `bun run e2e:down && bun run e2e:up && bun run e2e:bootstrap` is the way back.

The bootstrap seeds a native-SQL transform over the warehouse's orders table on any server that serves transforms, so the transform verbs and the transform tests have something to run against without a create command; a bootstrap file that predates that seed is extended on reuse by restoring the snapshot, seeding, and capturing it again. The probe cache the CLI writes goes to a per-file temporary `XDG_CACHE_HOME` (`CACHE_HOME` in `tests/e2e/run-cli.ts`), so a suite reads only the probes it seeded through `tests/e2e/seed-probe.ts`.

A green summary reports the lanes that ran. The closing coverage block reports the ones that did not and why — locally, absent an EE license token, that is every `remote_sync`-, `library`-, `transforms-testing`- and `serialization`-gated lane. A gate is `requireServer(lane, [<feature>])`, the same `checkFeatures` the CLI's preflight runs over the bootstrap's probe, so a lane skips exactly where the command would refuse; `serverHas(feature)` is for a suite that runs on every stack and asserts the outcome its generation produces. When pasting a run as evidence, paste that block too.

## Generated and vendored files

`packages/cli/src/core/schema/data/` holds the vendored `@metabase/representations` JSON schemas — the entity schemas beside `common/` — written by `scripts/sync-representations.ts` and reaching the CLI only as opaque `import … with { type: "json" }` payloads: `core/schema/validate.ts` compiles the MBQL query schema for `mb query`, `core/schema/representation.ts` one validator per `serdes/meta` model for `mb validate`. `packages/cli/src/core/schema/examples/` is the representation repository's example tree, a test fixture the unit tier holds the validator to. Both directories are in `.oxfmtrc.json`'s `ignorePatterns`: they are artifacts whose writer owns their bytes, and a formatter that reformats them turns every regeneration into a diff the other tool undoes. A generator writing under a formatted tree either emits the formatter's exact output or joins that list.
